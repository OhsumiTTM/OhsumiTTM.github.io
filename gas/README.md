# スプレッドシート連携セットアップ

Ohsumi は Google スプレッドシートを「データベース」として使います。
読み取り・書き込みとも Apps Script（GAS）の Web App 経由で行います。読み取りは
ログインした人の Google アカウントを GAS が確認し、閲覧権限のないデータを取り除いてから
返します。シートを「ウェブに公開」する必要はありません。

このドキュメントは **GitHub・GAS を使ったことがない人** にも迷わず設定できるよう書かれています。
用語の説明なども入れていますので、上から順番に読み進めてください。

---

## はじめに: 全体の流れ

```
Google スプレッドシート（データの保存場所）
        ↑↓ 読み込み・書き込み
   Apps Script Web App（ログインの確認・閲覧権限での絞り込み）
        ↑↓
   Ohsumi アプリ（GitHub Pages でホスト）
```

大まかな手順は次の 4 ステップです:

1. スプレッドシートにシートを作り、列を用意する
2. Apps Script（`Code.gs`）をスプレッドシートに貼り付けてデプロイする
3. GitHub の Secrets にURLなどを登録する
4. GitHub Actions でビルド・デプロイする

---

## 1. シートの列構成

`database.xlsx`（リポジトリのサンプル）と同じ列名・順序にしてください。
列名は1行目のヘッダーで判定するので位置がずれても動きますが、**列名は完全一致が必要**です。

> **用語: シートとは?**  
> Google スプレッドシートはExcelのように複数のシートをタブで切り替えられます。  
> ここでは `Members`・`Projects`・`Tasks` の 3 枚のシートを作ります。

### MemberEmails（メンバーのメールアドレス・非公開）

セキュリティ対応: メールアドレスはMembersシートには置かず、こちらの専用シートに分離しています。Membersシートの内容はログイン済みの全員に(閲覧権限に応じて)返すため、メールアドレスを置くと全メンバー分が全員に届いてしまうからです。

| 列名 | 内容 |
|---|---|
| id | Membersシートの `id` と同じ値 |
| email | 通知メールの送信先（新規タスク通知等に使用）。カンマ区切りで複数登録可。個人ページの「アカウント設定」から本人が編集できます |

> **重要**: このシートは**「ウェブに公開」しないでください**。`setupOhsumi()` を実行するとこのシートが無ければ自動作成されますが、公開設定は行われません（新規作成したシートはデフォルトで非公開です）。読み書きはすべて認証済みのGASアクション（ログイン時の`getInitialData`、本人のみが呼べる`getMyEmails`/`updateEmail`）経由で行われ、メールアドレスがフロントエンドに一括で渡ることはありません。

> 移行の途中で2つの形式が混ざっていても表示は変わりません。形式はスクリプトプロパティ `VALUE_FORMAT`
> で決まります(未設定は日本語、`codes` はコード)。**手で `VALUE_FORMAT` を設定しないでください**
> (新しく導入する団体では `setupOhsumi()` が、既存の団体では移行の関数が設定します。「2.2.」を参照)。

>

> 列として残しておいて構いません。
>
> 各シートの列は `Code.gs` の `SHEET_HEADERS` にまとめて定義しています。`setupOhsumi()` は、すべてのシート
> (Members・Projects・Tasks・Settings・MemberEmails・Expenses・FormSubmissions・DailyReports・Candidates)を作成し、
> 不足している列を末尾に追加します(既存の列・データは変えません)。**`Code.gs` を新しい版に貼り替えたら、
> 毎回 `setupOhsumi()` を実行してください**(新しい版で増えた列が追加されます)。

## 2. Apps Script のデプロイ

> **用語: Apps Script（GAS）とは?**  
> Google スプレッドシートに「プログラム」を書いて実行できる機能です。  
> Ohsumi はここに `Code.gs` を貼り付けることで、データの書き込み口（Web App）を作ります。

### 手順

1. スプレッドシートを開き、上部メニューの **「拡張機能」→「Apps Script」** をクリック
2. 開いたエディタの左側に `コード.gs` または `Code.gs` というファイルがある
3. その中身を**すべて選択して削除**し、リポジトリの `gas/Code.gs` の内容を丸ごとコピー&ペーストする
4. Google Sheets API のサービスを追加する(下の「2.1.」を参照)
5. 上部の「保存」ボタン（フロッピーアイコン or `Ctrl+S`）で保存する
6. 上部の **「デプロイ」→「新しいデプロイ」** をクリック
7. 「種類の選択」で **「ウェブアプリ」** を選ぶ
8. 設定を次のようにする:
   - **実行するユーザー**: `自分`
   - **アクセスできるユーザー**: `全員`
9. 「デプロイ」をクリック（初回は権限の確認画面が出ます → 「アクセスを許可」）
10. デプロイ後に表示される **`/exec` で終わる URL** をコピーしておく（後で Secrets に使います）

> **Code.gs を更新した場合（アプリのバージョンアップ時）**:  
> Apps Script エディタで内容を貼り直し → 「デプロイ」→「デプロイを管理」→  
> 対象のウェブアプリの編集（鉛筆アイコン）→「バージョン」で **「新規」** を選んで更新。  
> 「保存」だけでは既存のURLには反映されません。
>
> **関数の名前:** エディタの関数の一覧(▶ 実行の横)に出るのは、エディタから実行する関数(`setupOhsumi` など)と、
> ウェブアプリの入口・メニュー・トリガーから呼ばれる関数だけです。中で使うだけの関数は、名前の最後に `_` を付けて一覧から隠しています。
> エディタから実行する関数の一覧と、それぞれの説明は、`Code.gs` の先頭のコメントにあります。
> 貼り直した後は `setupOhsumi()` を実行してください。以前の版で作ったトリガーのうち、今の `Code.gs` に無い関数
> (消した関数・名前に `_` を付けた関数)を指すものを消します(残っていると、トリガーが動くたびにエラーになります)。
>
> **反映の順番**: GAS とフロント(GitHub Pages)の両方が変わる版では、**GAS を先に**反映してください。
> 新しいフロントは選択肢の値を内部コード(`done` など)で送るため、古い GAS では正しく保存できません
> (新しい GAS は、古いフロントが送る日本語の値も受け付けます)。
>
> **さらに、貼り直した Code.gs が Members/Projects/Tasks シートに新しい列を
> 追加している場合（例: `timezone`、`locale` 列の追加時）は、Apps Script
> エディタ上部の関数選択ドロップダウンで `setupOhsumi` を選び ▶ 実行ボタンを
> 押してください。** これを忘れると、新しい列を使う機能（タイムゾーン設定
> など）の保存が「エラーも出ずに何も保存されない」状態になります
> （列が無いため書き込み先が見つからず、静かにスキップされていました。
> 現在は列が1つも見つからない場合はエラーを返すよう修正済みです）。

### 2.1. Google Sheets API のサービス(マニフェスト `appsscript.json`)

シートの読み込みには、Sheets API(`values.batchGet`)を使います。Apps Script の「サービス」に
Google Sheets API が追加されていないと使えません(その場合は自動で `getDisplayValues` の読み方に
切り替わるため画面は動きますが、読み込みが遅くなります)。

必要な設定は、リポジトリの `gas/appsscript.json`(マニフェスト)に含めています。テンプレートの
スプレッドシートを「コピーを作成」で使う場合は、マニフェストもコピーされるため、追加の操作は不要な想定です
(コピー後に `measureReadD()` を実行し、`HTTP 403` が出ないことを一度確認してください)。

テスト環境や、既にある環境で追加する場合は、次のどちらかを行います。

- **A. エディタで追加する(おすすめ)**: Apps Script エディタ左の **「サービス」の「+」** →
  **「Google Sheets API」** を選び、バージョン `v4`・ID `Sheets` のまま **「追加」**。
  Google Cloud のコンソールでの操作は不要です。
- **B. マニフェストを貼り替える**: 「プロジェクトの設定」(歯車)→ **「「appsscript.json」マニフェスト ファイルを
  エディタで表示する」** にチェック → エディタに出る `appsscript.json` に、リポジトリの `gas/appsscript.json`
  の `dependencies` の部分を反映する。`timeZone` は今の値のままにしてください(`Asia/Tokyo` 以外で
  運用している場合に、日付の計算が変わるため)。

どちらの場合も、追加後に「デプロイを管理」から新しいバージョンでデプロイし直してください。
新しい権限は使わないため、承認の画面は出ない見込みです(スプレッドシートと外部への接続の権限は、
既に承認済みのものを使います)。

**確認**: エディタで `measureReadD()` を実行し、実行ログに `HTTP 403 PERMISSION_DENIED / SERVICE_DISABLED` が
出ないこと、「結果の一致(getDisplayValues と比べて): 一致」と出ることを確認します。本番の読み込みで
Sheets API が失敗した場合は、実行ログ(「実行数」)に `readSheetTables: Sheets API で読み込めなかったため…
理由: …` という警告が残ります。

### 2.2. 新しく導入する団体・テンプレートのコピーと、選択肢の値の形式

`setupOhsumi()` は、選択肢の値(ステータスなど)をシートに書く形式を、次のように決めます。
結果は実行ログに出ます。

| スプレッドシートの状態 | `setupOhsumi()` の動き |
|---|---|
| データ行が1行も無い(見出しだけ。新しく導入する団体) | スクリプトプロパティ `VALUE_FORMAT` を `codes` にし、最初からコードで書き込みます |
| どこかのシートにデータ行がある | `VALUE_FORMAT` は変えません(今の日本語のまま書き込みます)。コードへの移行は、移行の関数 `migrateToInternalCodes()`(「4.6.3.」)で行ってください |
| 既に `VALUE_FORMAT` が `codes` | そのままです |

「データ行」は、どれかのシート(Members・Projects・Tasks・経費・フォームの回答など)の2行目以降です。
Settings シートは、`setupOhsumi()` が作る初期キー(団体名など)を数えず、テンプレート・定期タスク・
スキルの閾値の設定が入っている場合だけデータとして数えます。

**テンプレートのスプレッドシートを「コピーを作成」して導入する場合**:
スプレッドシートをコピーすると、Apps Script のコードはコピーされますが、**スクリプトプロパティは
引き継がれません**(`VALUE_FORMAT`・ログインの団体ID `ORG_ID`・秘密鍵なども同じです)。これは問題ありません。
コピーの後に「2.」の手順どおり `setupOhsumi()` を実行すると、必要なスクリプトプロパティがそのコピーの
ために新しく作られます。テンプレートが見出しだけなら `VALUE_FORMAT` は `codes` になります。
テンプレートにデータ行が入っていた場合は日本語で書き込む設定のままになりますが、読み込みはどちらの
形式にも対応しているので、動作に問題はありません。

**`VALUE_FORMAT` とシートの値の形式が食い違った場合**(バックアップから戻した、別の団体のシートを
取り込んだなど): 読み込み・権限の判定は、日本語・コードのどちらの値も受け付けるので、表示や動作は
壊れません。以降に書き込む値だけが `VALUE_FORMAT` の形式になるため、2つの形式が混ざった状態に
なります。移行の関数で1つの形式にそろえられます。

## 4. GitHub Secrets の設定

> **用語: GitHub Secrets とは?**  
> パスワードや秘密URLなど「コードに直接書きたくない値」を安全に保存しておける場所です。  
> ビルド時に GitHub Actions が自動的に読み込みます。

### 必須の Secrets

リポジトリの **「Settings」→「Secrets and variables」→「Actions」→「New repository secret」** から追加します。

| Secret名 | 値の取得場所 | 説明 |
|---|---|---|
| `REGISTRY_URL` | レジストリのウェブアプリの URL(`registry/README.md` の 1.5) | 団体の接続先の解決(招待リンクの団体ID → 団体の GAS の URL)と、レジストリの管理画面 `/registry-admin/` |
| `GOOGLE_OAUTH_CLIENT_ID` | 後述「4.1」参照 | ログイン認証（Googleサインイン） |

団体の GAS の URL(手順2でコピーした `/exec` で終わる URL)は、Secrets には入れません。団体の担当者が、スプレッドシートの
「Ohsumi」→「レジストリに登録する…」でレジストリに登録し、メンバーは招待リンク(`<サイトの URL>/?org=<団体ID>`)から開きます。
以前の `CSV_GAS`(ビルド時の既定の団体)は、R1-f 後半で使わなくなりました。残っていれば、Secrets から消してください。

### 任意の Secrets

| Secret名 | 説明 |
|---|---|
| `FEEDBACK_FORM_URL` | フィードバックの送信先 Google フォームの `formResponse` で終わるURL |
| `GOOGLE_CALENDAR_READ` | `true` にすると、Googleカレンダーの予定の表示と日程候補の空き時間の確認を有効にします(機密のスコープ `calendar` を要求します。Google の審査を通過するまでは設定しないでください) |
| `REGISTRY_OAUTH_CLIENT_ID` | レジストリの管理画面のログインに使う、レジストリ用の OAuth クライアント ID(同上。Ohsumi 本体のクライアントとは別) |

**注意**: 静的サイトとしてビルドされるため、Web App の URL と OAuth クライアントIDはビルド後のJavaScriptから誰でも読み取れます。ただし、データの読み書きには Google アカウントでのログインが必要で、閲覧権限のないデータは Apps Script が返しません。

## 4.1. Google OAuth クライアントID の設定（Googleサインイン）

Ohsumi のログインには Google アカウントでのサインインを使います。
そのために Google Cloud Console でクライアントIDを取得する必要があります。

> 初めての方は少し複雑ですが、一度設定すれば変更の必要はありません。

### 手順

1. [Google Cloud Console](https://console.cloud.google.com/) を開く
2. 左上のプロジェクト選択から **「新しいプロジェクト」** を作成（名前は何でもOK）
3. 左メニューの **「APIとサービス」→「OAuth 同意画面」** を開く
   - ユーザーの種類: **「外部」** を選択 → 「作成」
   - アプリ名・メールアドレスを入力 → 「保存して次へ」を何度かクリックして完了
4. 左メニューの **「APIとサービス」→「認証情報」** を開く
5. 上部の **「認証情報を作成」→「OAuthクライアントID」** をクリック
6. アプリケーションの種類: **「ウェブアプリケーション」** を選択
7. 「承認済みのJavaScriptオリジン」に以下を追加:
   - `https://<GitHubユーザー名>.github.io`（GitHub Pages のURL）
   - `http://localhost:3000`（ローカル開発用、任意）
8. 「作成」をクリック → **「クライアントID」** をコピー（`123456789-xxxx.apps.googleusercontent.com` の形式）
9. このIDを GitHub Secrets の `GOOGLE_OAUTH_CLIENT_ID` に登録する

#### 要求するスコープ

フロントが要求するスコープは、非機密のものだけです(Google Auth Platform の「データアクセス」に、この3つを登録します)。

| スコープ | 用途 | 要求するタイミング |
|---|---|---|
| `openid` | ログイン(Google Identity Services の IDトークン) | 「Googleでログイン」を押したとき、Googleの自動ログインのとき |
| `.../auth/userinfo.email`(`email`) | ログインしたメンバーの特定 | 同上 |
| `.../auth/drive.file` | 個人スプレッドシート連携(アプリが作成したシートにだけ書き込む) | 個人ページで「同期用のスプレッドシートを作成」「今すぐ同期」を押したとき |

- タスクや不在日の Googleカレンダーへの追加は、Googleカレンダーの新規予定画面を開くリンクで行うため、スコープは不要です
- Googleカレンダーの予定の表示と空き時間の確認は、機密のスコープ(`.../auth/calendar`)が必要なため停止しています。Secret `GOOGLE_CALENDAR_READ` を `true` にすると有効になります
- 個人スプレッドシート連携には、OAuth クライアントのプロジェクトで **Google Sheets API** が有効になっている必要があります(「APIとサービス」→「ライブラリ」)

#### Apps Script にも登録する

同じIDを Apps Script の「スクリプトプロパティ」にも登録します:

1. Apps Script エディタを開く
2. 左メニューの **「プロジェクトの設定」（歯車アイコン）**
3. 「スクリプト プロパティ」→「プロパティを追加」
4. プロパティ名: `GOOGLE_OAUTH_CLIENT_ID`、値: 上でコピーしたクライアントID

> **`GOOGLE_OAUTH_CLIENT_ID` の設定は必須です。** 以前は未設定の場合に
> クライアントIDの検証をスキップする「簡易モード」がありましたが、
> なりすましトークンを弾けなくなるセキュリティ上の問題があったため廃止
> しました。未設定のまま利用しようとすると、ログイン時にエラーになります。

## 4.2. ログインの仕組み(IDトークンとセッション)

### 流れ

1. ログイン画面は、Apps Script の `getLoginConfig` から団体ID(スクリプトプロパティ `ORG_ID`)と、提供停止中かどうかを受け取る。
   この端末の団体の一覧(`ohsumi-orgs`)にある団体は、**保存した団体ID ですぐにログインボタンを出し**、`getLoginConfig` は裏で確かめます。
   答えが同じなら何も作り直さず、違う時(別の団体ID・提供停止中)だけ画面を切り替えます。答えを待つのは、招待リンクで初めて開いた端末だけです
   (レジストリの答えの接続先が、本当にその団体の GAS かを確かめるため)。OAuth のクライアントID はビルド時に決まるので、`getLoginConfig` からは受け取りません
2. 「Googleでログイン」(または Google の自動ログイン)で、Google が IDトークンを発行する。IDトークンの
   `nonce` には、団体IDと、その画面だけが知る乱数のハッシュが入る
3. Apps Script の `exchangeIdToken` が、tokeninfo で IDトークンの署名・有効期限を確認し、
   `aud`(クライアントID)・`iss`・`email_verified`・`nonce`(この団体・この画面のものか、使い回しでないか)を確かめる
4. 登録済みのメンバーなら、**この団体の Apps Script だけが持つ秘密鍵**で署名した「セッショントークン」を発行する
5. 以降の通信はセッショントークンだけで本人を確認する(Google への問い合わせはしない)

ある団体の Apps Script に送ったトークンを、別の団体の Apps Script で使うことはできません(団体ID・秘密鍵が違うため)。

### 有効期間と保存場所

| ログイン画面の「この端末にログイン情報を保存する」 | 保存場所 | 有効期間 |
|---|---|---|
| チェックあり(初期値) | ブラウザの localStorage(再読み込み・再起動後もログインしたまま) | 1回14日。使っている間は自動で延長し、Googleでのログインから最長30日 |
| チェックなし | ブラウザの sessionStorage(タブを閉じると消える) | 12時間(延長しない) |

期限が切れた場合や無効になった場合は、ログイン画面に戻ります(Google の自動ログインが使える場合は、ボタンを押さずにログインし直せます)。

### 全端末でログアウト

- 本人: 個人ページの「設定」→「ログイン中の端末」→「全端末でログアウト」
- 管理者(代表・全権管理者): 管理画面の「メンバー」→ 各メンバーの「全端末でログアウトさせる」

メンバーごとの世代番号(スクリプトプロパティ `SESSION_GEN_<メンバーID>`)を1つ上げ、発行済みのセッションを
すべて無効にします。メンバーを削除した場合と、登録していたメールアドレスを外した場合も、自動で無効になります。
この端末だけのログアウトでは、ブラウザに保存したログイン情報を消します(コピーされていた場合、そのコピーは有効期限まで残ります)。

### スクリプトプロパティ

`setupOhsumi()` を実行すると、無ければ自動で作成します(既にあれば変えません)。1回のリクエストで
`getProperties()` を1回だけ読み、まとめて使います。

| プロパティ | 内容 |
|---|---|
| `ORG_ID` | 団体ID(IDトークンの nonce とセッショントークンに入る) |
| `SESSION_SIGNING_KEY` / `SESSION_KEY_ID` | セッショントークンの署名に使う秘密鍵と、その鍵のID。**この団体の Apps Script にだけ置き、FSIF を含め誰にも渡さないでください** |
| `SESSION_NOT_BEFORE` | この時刻(秒)より前に発行されたセッションを無効にする |
| `SESSION_GEN_<メンバーID>` | メンバーごとの世代番号(全端末でログアウト) |
| `REGISTRY_URL` / `OHSUMI_WEBAPP_URL` | レジストリの URL と、この GAS のウェブアプリの URL(レジストリへの登録に使う。手で入れる。`registry/README.md` の 4.2) |
| `REGISTRY_SHARED_KEY` / `REGISTRY_KEY_GEN` / `REGISTRY_REGISTERED_AT` | レジストリとの共有鍵・その世代・登録した日時(「Ohsumi」→「レジストリに登録する…」が保存する。**共有鍵は表示・共有しないでください**) |
| `REGISTRY_PENDING` | 登録の途中で応答が失われた時に、同じ登録として送り直すための乱数(registerNonce。レジストリはこれが合う時だけ、24時間まで同じ共有鍵を返す)と、登録コードの SHA-256(登録できたら消える。**ほかに写さない**) |
| `INITIAL_SETUP_HASH` / `INITIAL_SETUP_EXPIRES` / `INITIAL_SETUP_FAILS` | 最初の代表の初期設定コードの SHA-256・有効期限(72時間)・間違えた回数(使うと消える) |
| `CONTRACT_STATE` | レジストリで最後に確かめた停止の状態(4.2.1。`checkContractStatus` が書く。手で変えない) |
| `CONTRACT_NOTICES_SENT` | 代表に送った停止の予告(予定の日時と種類ごとに、14・7・1日前のどれを送ったか) |

`LEGACY_ACCESS_TOKEN_AUTH` が残っている場合は、今は使っていないので削除して構いません。

### スプレッドシートの「Ohsumi」メニュー(レジストリへの登録)

スプレッドシートを開くと、上部に「Ohsumi」メニューが出ます(`onOpen`)。登録コード・初期設定コード・共有鍵を
実行ログに残さないため、エディタからではなく、このメニューから行います(手順は `registry/README.md` の「4. 新しい団体の立ち上げ」)。

| メニュー | 内容 |
|---|---|
| レジストリに登録する… | FSIF から受け取った登録コード(または再登録コード)を入れ、レジストリに登録して共有鍵を受け取る。代表がいなければ、最初の代表の初期設定コードをダイアログに1回だけ出す |
| 初期設定コードを作り直す | 代表がいない時だけ。前のコードは使えなくなる |

### エディタから実行する関数

| 関数 | 内容 |
|---|---|
| `rotateSessionKey()` | 秘密鍵を作り直す。**全員のログインが一度無効になり**、次の操作でログイン画面に戻ります(秘密鍵が漏れた疑いがある場合、スクリプトを編集できた人が抜けた場合など) |
| `revokeSessionsIssuedBefore()` | 今より前に発行されたセッションをすべて無効にする |
| `revokeSessionsIssuedBeforeInput()` | スクリプトプロパティ `REVOKE_BEFORE_INPUT` に書いた日時(例: `2026-10-01T09:00:00+09:00`)より前に発行されたセッションを無効にする(将来、FSIF のレジストリからの指示で同じことを行う予定です) |

### 4.2.1. 提供停止・機能停止(R1-e)

FSIF がレジストリの管理画面で停止の予定を入れると、この GAS は次のように動きます(停止の種類と予告は `registry/README.md` の「1.9」)。

- **確認:** 1時間ごとのトリガー `checkContractStatus` が、レジストリの `checkIn` に状態を確かめ、スクリプトプロパティ `CONTRACT_STATE` に覚えます。
  トリガーは `setupOhsumi()` が作ります。**R1-e の版に貼り替えた後は、`setupOhsumi()` を実行してください。**
  - 共有鍵(`REGISTRY_SHARED_KEY`)で署名を付けて送ります。共有鍵そのものは送りません。レジストリに登録していない団体は確かめません。
  - リクエストの時にも確かめ直します。停止中はどの操作でも1分に1回まで、停止の予定がある時は書き込みの前に1分に1回まで、
    予定が無い時は書き込みの前に10分に1回まで(`registry/README.md` の「1.9」)。
  - レジストリに確かめられない時は、最後に確かめた状態のまま使い続けます(最後に届いた停止の予定の日時は守ります)。
- **① 提供停止中:** ログインの設定(`getLoginConfig`)以外のすべての操作を断ります(`orgSuspended`)。画面はログイン画面に戻り、
  「この団体は、Ohsumi の利用を停止しています」を出します。通知(`sendBatchNotifications`)・毎朝の処理(`dailyMaintenance`)も止めます。
- **② 機能停止中:** 読み取りの一覧(`READ_ONLY_ACTIONS`。ログイン・読み取り(`getInitialData`・`getExpenses`・`getFiles` など))に
  無い操作は、すべて断ります(`restricted`)。まとめて送る書き込み(batch)も断ります。新しく足した操作も、一覧に足さない限り断ります
  (`lib/ohsumi/gas-contract.test.ts` が、受け付けるすべての操作を1本ずつと batch で送って確かめます)。
  画面の上部に「アンケートへの回答をお願いします。回答が確認でき次第、再開します」を出します。通知・毎朝の処理は止めません。
  画面は、書く欄を最初から使えなくし、作成・編集を保存の手前で止めます(`registry/README.md` の「1.9」の「読み取り専用の画面」)。
- **テスト環境で確かめる:** 14日待たずに確かめる手順は、`registry/README.md` の「1.9.1」にあります。
- **予告:** 停止の14日前・7日前・1日前に、代表(最上位の役職のメンバー)にメールで知らせます(停止の理由も書きます)。画面にも14日前から上部に出します。
- **データ:** どちらの停止でも、スプレッドシートのデータは消しません。解除すれば、そのまま元に戻ります。

### セキュリティ上の注意

- ブラウザに保存したログイン情報が盗まれた場合、その人として、この団体だけで、有効期限まで操作できます。
  心当たりがある場合は「全端末でログアウト」、全員分なら `rotateSessionKey()` を実行してください
- **このアカウント(OhsumiTTM)では、他のリポジトリを GitHub Pages で公開しないでください。** 同じアカウントの
  Pages は同じ場所(オリジン)で配信され、そのページのスクリプトから保存したログイン情報を読み取れてしまいます。
  独自ドメインに移行した後も、同じアカウントの他のリポジトリの Pages は同じドメインの下で公開されるため、
  このルールは引き続き必要です
- 共用のパソコンでは、ログイン画面のチェックを外すよう案内しています

## 4.3. 通信の送り方と再試行

Apps Script の Web アプリは、処理の結果を `script.googleusercontent.com` の echo の URL へ転送して返します。
GAS の処理は成功しているのに、この転送先が 404 になり、画面が JSON を受け取れないことがあります
(同じ端末から同時に何本も送った時に起きやすい)。そのため、画面は次のように送ります(`lib/ohsumi/gas-transport.ts`)。

- **画面は、保存の応答を待たずに変更を表示します**(楽観的な更新)。タスクの日程・優先度・難易度・詳細・前提タスク・確認者は、
  **保存に失敗した時だけ、その項目と変更の記録を元に戻し**、「保存できなかったため、変更を元に戻しました」と知らせます。
  保存を待っている間に同じ項目をさらに変えていた時は、新しい変更を消さないよう戻しません(`lib/ohsumi/optimistic.ts`)
- **書き込みは1本ずつ、呼ばれた順に送ります。** 画面の1回の操作から続けて呼ばれた書き込み(例: 日程の変更は、
  変更の記録 `updateHistory` と `updateSchedule`)と、前の書き込みを送っている間に呼ばれた書き込みは、**1回の通信(`batch`)にまとめます**
  (最大20件)。GAS は、中の操作ごとに1本ずつ送った時と同じ権限の確認をして順番に実行し、ロック・送り直しの記録・版の更新はまとめて1回にします。
  1つが断られても・失敗しても、ほかの操作は実行し、結果は操作ごとに画面へ返します。同じタスクの変更の記録(配列を丸ごと置き換える)が
  同じ束に2つ以上あれば、最後のもの(前の記録を含む)だけを送ります。ファイルのアップロードと、GAS がロックを取らない操作はまとめません。
  - **片方だけ成功すると困る組み合わせ**は、前提の操作(変更そのもの)を先に実行し、前提が断られた・失敗した時は実行しません
    (`skipped: true`。`BATCH_SKIPPED_ERROR` の文言を返します)。画面は記録などを変更より先に送るので、実行の順番も入れ替えます(`batchPrerequisites_`)
    - 変更の記録(`updateHistory`) ← 記録した項目を変える操作(同じタスク。期限・開始日なら `updateSchedule`、優先度なら `updatePriority`・`updateTaskDetails` など)
    - 回答がそろった通知(`notifyScheduleResult`・`notifyFormResult`) ← 回答の保存と完了への変更(同じタスク)
    - メンションの通知(`notifyMention`) ← コメントの保存 / 却下の通知(`notifyTaskRejected`) ← タスクの削除
    - 担当者をプロジェクトに加える(`updateProjectMembers`) ← 担当者の変更(そのプロジェクトのタスク)
    - 完了で付くスキル・認定(`updateSkillLevels`・`updateJudgment`) ← 完了への変更(そのメンバーが担当のタスク)
    - 確認タスクの作成(`createTasks`) ← 確認待ちへの変更(元のタスク)
    - 前提の操作が同じ束に無い時(別々に送られた時)は、これまでどおり実行します
  - **送り直し(requestId)は、まとめた1本ごとです。** 同じ束を送り直す時は同じ `requestId` を付け、GAS は前回の結果
    (中の操作ごとの結果を含む)を返し、中の操作をもう一度実行しません(`lib/ohsumi/gas-write-auth.test.ts`)
  **GAS が古い(`batch` を知らない)時は、1本ずつ送り直し、そのページでは以後まとめません**(反映は GAS → 画面の順にしてください)。
  読み取りは3本まで同時に送ります。1本が詰まっても
  (echo の 404・打ち切り・再試行)、ほかの読み取りは待たされません。画面の操作に必要な読み取り(初期データなど)を、
  裏での読み込みより先に送ります。初期データは、それより前に呼ばれた書き込みが終わってから送ります
- **ログイン・再読み込み・情報更新は、それぞれ通信1回です。** `exchangeIdToken`・`getInitialData` に `withBackground: true` を付け、
  初期データと同じ応答で、裏での読み込み(経費・フォームの回答・採用の候補者・自分のメールアドレス。`getBackgroundData` と同じもの)も
  受け取ります(それぞれ個別の操作と同じ絞り込みを通ります。1つが失敗しても、ほかは受け取ります)。
  往復の回数が減るほど、結果の受け渡し(echo)で止まる機会が減ります。裏での読み込みだけ失敗した時(`backgroundError`)と、
  GAS が古い(`background` を返さない)時は、画面が `getBackgroundData` を別に送ります
- **ログインの最終ログイン日時は、ログインの応答を待たせずに記録します**(画面は `updateLastLogin` を送りません)
  - 前回の記録から1時間以内なら、何もしません
  - それ以外は、スクリプトプロパティの書き込み待ちに入れるだけです(ロックもシートも使いません)。書き込み待ちは、ログイン1回ごとに別のプロパティ
    (`LAST_LOGIN_PENDING_<メンバーID>_<時刻>_<乱数>`)にします。全員分を1つにまとめないので、同時にログインしても互いに消し合いません。
    シートに書いた後は、書く前に(ロックを取ってから)読んだキーだけを消すので、書いている間のログインも残ります
  - **トリガーが止まっていても増え続けません。** 1時間以内の判定には、シートの値に加えて、そのメンバーの書き込み待ちの日時も使います。
    新しく入れる時は、そのメンバーの古い書き込み待ちを消して1件に置き換えます。書き込み待ちが200件(`LAST_LOGIN_PENDING_MAX`)に達したら、
    まだ書き込み待ちの無いメンバーの分は入れずに捨てます(内訳に `書き込み待ちが上限のため記録せず`)
  - 書き込み待ちは、毎時のトリガー(`sendBatchNotifications`)と毎日のトリガー(`dailyMaintenance`。活動のないメンバーの判定より前)が、
    まとめて Members の `last_login` に書きます(`flushPendingLastLogins_`)。**画面の最終ログイン日時は、最大1時間ほど遅れて反映されます**
  - データの版は変えないので、ほかのメンバーの画面の最終ログイン日時は、次に版が変わった時に新しくなります
- **裏での読み込みはキャッシュから返します。** 経費・フォームの回答・採用の候補者は、シート1枚分の行を**表ごとの版**でキャッシュします
  (作ってから5分で作り直します)。閲覧できるかの絞り込みは、毎回メンバーごとに行います。シートは1回の呼び出し(`getDataRange`)で読みます。
  - **キャッシュに無い表(経費・フォームの回答・候補者・メールアドレス表)が2つ以上ある時は、Sheets API を1回だけ呼んでまとめて読みます**
    (`prefetchBackgroundSheets_`)。`values.batchGet` は日付をシリアル値(数)で返し、日付と数を区別できないため、セルの値と表示形式の種類を
    一緒に返す `spreadsheets.get`(`includeGridData`)を使い、値を SpreadsheetApp の `getValues` と同じ形(日付・時刻の表示形式のセルは
    スプレッドシートのタイムゾーンの `Date`、数は数、文字は文字、空は `""`、エラーは `#N/A` など)にそろえます。1枚ずつ読んだ時と
    同じ結果になることは `lib/ohsumi/gas-batch-read.test.ts` で確かめています。API で読めなかった時は、これまでどおり1枚ずつ読みます
  - 候補者は採用の権限を持つ人の時だけ読みます。キャッシュに無い表が1つだけの時は、これまでどおり1枚で読みます
- **版は表ごとに分けます。** スナップショット(Members・Projects・Tasks・Settings)・経費・フォームの回答・候補者の4つ(と、メールアドレス表)。
  - アプリからの書き込みは、その操作が書くかもしれない表の版だけを変えます(`TABLE_WRITE_ACTIONS`・`SNAPSHOT_UNTOUCHED_ACTIONS`)。
    タスクの書き込みで、経費などのキャッシュは捨てません。一覧は、`scripts/gas-write-tables.mjs` が Code.gs の呼び出しをたどって調べた結果を
    必ず含むことをテストで確かめます(新しい操作を足した時に、一覧への書き忘れに気付けます)
  - メンバー・役職・部門などの書き込みは、必ずスナップショット(読み取りの権限の判定に使う)の版を変えます
  - スプレッドシートを直接編集した時は、編集のトリガー(`onSpreadsheetEdit`)が、**編集したシートの版だけ**を変えます。
    行の追加・削除・シートの追加など、どのシートか分からない変更(`onSpreadsheetChange`)と、知らないシートの編集は、すべての版を変えます。
    **編集のトリガーは `setupOhsumi()` が作ります。この版に更新した団体は、`setupOhsumi()` を一度実行し直してください**
    (実行し直すまでは、これまでどおり編集のたびにすべての版を変えます)
  自分のメールアドレスは、メールアドレス表の版ごとにキャッシュします。フォームの定義は、スナップショットの Settings から読みます
- **ログインの応答に、画像も入れます。** 団体ロゴ・本人・ほかのメンバーのプロフィール画像のうち、GAS のキャッシュにあるもの
  (最大30件・合計約1.5MB)を入れ、画面は `getFiles` を送らずに表示します。キャッシュに無い画像は、これまでどおり画面が `getFiles` で取ります
  (取った画像はキャッシュに入るので、次のログインからは応答に入ります)
  - 画像を入れると応答が大きくなり、結果の受け渡し(echo)に時間がかかる可能性があります。コンソールの行の `応答 ◯KB` と
    `画像 40(3件 180KB)` で大きさを確かめ、ブラウザのコンソールで `ohsumiInitialImages(false)` を実行すると、次のログイン・再読み込みから
    画像を入れません(この端末のブラウザだけ。`ohsumiInitialImages(true)` で元に戻します)。入れた時と入れない時の往復の時間を比べて、上限を決めてください
- **`getFiles` はファイルの種類もキャッシュします**(ファイルIDは変わらないため)。2回目からは、キャッシュにある画像を Drive を開かずに返します。
  アップロード用フォルダの外のファイルは覚えません。領収書は、権限をキャッシュした経費で毎回確かめ、中身はキャッシュしません
- **定期タスクの生成は、時間主導トリガー(`dailyMaintenance`、毎日6時台)に任せます**(画面からは確認しません)
- **読み取りと普通の書き込みの認証は、初期データと同じ読み取りキャッシュ(スナップショット)から**メンバー・役職の設定・
  担当者の確認に使うタスクの行を引きます(Members・Settings・Tasks をシートから読み直さないので、認証が速くなります)。
  キャッシュが無ければ、Sheets API の1回で作り直します(次の読み取りでも使えます)。
  権限そのものを変える操作(`SHEET_AUTH_ACTIONS`)は、これまでどおりシートから読みます。書き込みは、ロックを取った後に版をもう一度確かめ、
  判定の後に版が変わっていたらシートから判定し直します(「既知の制約」の運用上の注意も参照)
- **JSON が返らなければ、1秒・3秒待って送り直す(最大3回)。** 読み取りはそのまま送り直します
- **書き込みにはリクエストごとの ID(`requestId`)を付けます。** GAS は、同じメンバー・同じ ID の応答を
  10分覚えておき(CacheService)、送り直された時は処理をやり直さずに前回の応答を返します(`replayed: true`)。
  同じ ID の処理がまだ終わっていない時と、ロックを取れなかった時(まだ何も処理していない)は `retryLater` を
  返し、画面はもう少し待って送り直します
- **`exchangeIdToken`(ログイン)も、同じ `requestId` のまま送り直します**(ほかの書き込みとはまとめません)。GAS は、
  `requestId`・IDトークン・画面の乱数(nonceSecret)の3つを合わせたハッシュを鍵に、ログインの結果を10分覚えておき、
  送り直された時は IDトークンを確かめ直さずに**同じセッション**を返します(`replayed: true`)。初期データは大きいので覚えず、
  画面は受け取ったセッションで初期データを読み直します(`reloadInitialData`)。失敗した時は同じ失敗を返します。
  - **安全性:** 覚えた結果を受け取れるのは、同じ3つを送れる人だけです。画面の乱数は、IDトークンを受け取ったそのページの中にしか無く
    (保存も送信もログイン1回だけ)、IDトークンが漏れても乱数が無ければ受け取れません。乱数が違う・`requestId` が違う時は、
    これまでどおり IDトークンを確かめ、nonce は1回しか使えないので「既に使われています」で拒否します。覚えておく鍵はハッシュで、
    乱数・IDトークンそのものは覚えません。覚えておく先(CacheService)は GAS の中だけで、外からは読めません
  - GAS がまだ前のログインを処理している時は `retryLater` を返し、画面はもう少し待って送り直します
- ログインに失敗して、もう一度ログインしてもらう時は、ページを読み込み直してから新しい試行を準備します
  (同じページで `google.accounts.id.initialize()` を2回呼ばないため。失敗の知らせは、読み込み直した画面に1回だけ出します)
- IDトークンの確認は、これまでどおり Google の tokeninfo に問い合わせます(1回 数百ms〜3秒ほど。ログインの時だけで、以降の通信では問い合わせません)
- 3回送っても受け取れなければ、画面に「読み込みに失敗しました」と「もう一度試す」を出します
- **ログイン画面に戻すのは、セッションが無効・期限切れの時だけです。** GAS は、セッションが無い・無効・期限切れ・メンバーが見つからない時だけ
  `authError: true` を返し、画面は保存したセッションを消してログイン画面に戻します。権限が足りない時は `forbidden: true` を返し、
  画面はその操作だけ失敗として扱います(ログインはそのまま)。裏での読み込みが失敗した時も、小さな通知と「もう一度試す」だけです
- **裏での読み込みのうち、権限の無い部分は空で返します**(一般のメンバーに候補者が無いのは正常なので、失敗にしません)
- ログアウト・セッション切れでログイン画面に戻る時、そのページで Google のログインを準備済みなら、ページを読み込み直します
  (同じページで `google.accounts.id.initialize()` を2回呼ばないため)
- 1回の送信は、読み取りは20秒・書き込みは45秒で打ち切って送り直します(止まった1本がほかを待たせないように)
- **Google のログイン情報(Cookie)は送りません**(`credentials: 'omit'`)。転送(302)はたどります
- **GAS に GET で届いた時**は、`doGet` がシートもプロパティも読まずに `getReceived: true`・`bounced: true` の JSON を返します
  (何も処理していません)。結果の受け渡し(echo)が、返事を渡さずに exec への GET に送り返した時に起きます
  (URL が `/exec` ではない時にも起きます)。**読み取りは待たずにすぐ送り直します。** 書き込みは同じ `requestId` のまま、
  いつもの待ち時間(1秒・3秒)の後に送り直します(二重に処理されません)。
  送り返された GET そのものが止まった時は、打ち切り(20秒)まで待ちます(ブラウザは転送の途中の状態を画面に渡さないため)
- **切り分け用の `ping`:** GAS は認証もシートの読み込みもせずに、すぐ返します。ブラウザのコンソールで `ohsumiPing()` を実行すると、
  3回送り、1回ごとに往復の時間・exec と echo の内訳・GAS の中の時間を並べて出します(`ohsumiPing(10)` で10回)。
  ping でも往復が長い時は、GAS の処理ではなく Google 側か回線側で時間がかかっています

### コンソールの記録

| 記録 | 意味 |

| `[ohsumi] ログインからすべてのデータがそろうまで 3200ms` | ログイン(または再読み込み)から、初期データと裏での読み込みがそろうまでの時間 |
| `… 再試行 1/2(原因: …)` | 送り直した回数と原因 |
| `… JSON ではない応答(HTTP 404)。応答の URL: https://script.googleusercontent.com/macros/echo?…(転送あり)、本文の先頭: …` | JSON ではない応答。最終的に応答した URL(クエリは除く)と、本文の先頭300文字(タグを除き、トークンのような値は伏せる。JSON の断片は出さない) |
| `… GAS に GET で届きました(結果の受け渡し(echo)が exec への GET に送り返した)。…、10570ms` | `doGet` が応答した(最後はそこまでの時間)。読み取りは `再試行 1/2(すぐ送り直します)` が続きます |
| `[ohsumi] ping 1/3: 往復 10900ms(exec 10770ms・echo 130ms)・GAS の中 2ms` | `ohsumiPing()` の結果 |

- **往復と GAS の時間の差が大きい**時は、GAS の外(Google の転送・echo・通信)で時間がかかっています
- **裏での読み込み**: `withBackground` で同じ応答に入れた裏での読み込みの時間
- **キャッシュ**: `unchanged`(版が同じで中身を送らない)・`hit`(キャッシュから)・`miss`(シートから読んだ)。
  `miss` が続く時は、データの版が頻繁に変わっています(書き込み・スプレッドシートの手動の編集・定期タスクの生成で変わります)
- **シート読み込み**: `Sheets API` が通常。`予備の方式` の時は、Sheets API で読めなかった理由も出ます
- **ロック待ち**: 書き込みだけ。読み取りはロックを取りません
- **認証**: `認証 12(キャッシュ)` はスナップショットで判定したもの、`(シート)` はシートから読んで判定したもの(権限そのものを変える操作・
  スナップショットに見つからない時)。`権限の判定し直し` は、ロックを取った後に版が変わっていてシートから判定し直した時の時間
- **書き込みの内訳**: `送り直しの確認と記録`・`処理 850(行の読み込み 100・シートへの書き込み 300・通知の準備 50・メール 400(2件)・
  チャット・カレンダー・そのほか 0)`・`書き込みの確定 700`・`版の更新 40`。
  - `シートへの書き込み` は、書く行を探す読み込みを含みます。セルへの書き込みは、Apps Script がまとめて後で確定させるため、
    その時間は多くが `書き込みの確定`(`SpreadsheetApp.flush()`。ロックを放す前に行う)に入ります
  - `通知の準備` は、通知の本文を作るなどの時間(宛先・言語を調べる時間は `宛先を調べる`、メールの送信は `メール`)。
    `そのほか` は、処理のうち上のどれにも入らない時間
  - **行への書き込み**(`updateRowFields_`)は、シートを1回の呼び出し(`getDataRange`)で読み、同じ実行の中の2回目からは読み直しません
    (見出しと ID → 行番号を覚える。行を削除した時は忘れ、見つからない ID があった時だけ読み直す)。
    同じ行の隣り合う列は1回の `setValues` にまとめ、離れた列は間のセル(数式など)を書き換えないよう別に書きます
  - **通知の準備**は、宛先・言語(担当者の上長・通知を受け取るメンバー・管理者・言語)をスナップショットのメンバーと、
    メールアドレス表の版ごとのキャッシュから引き、団体の通知先はスナップショットの設定から引きます(シートを読み直しません)。
    書いたばかりのタスクの行は読み直さず、この実行で覚えている行(書いた値を含む)か、権限の判定に使ったスナップショットの行を使います
    (`requestRow_`。通知の本文にだけ使い、判定には使いません)
  - `batch(updateHistory+updateSchedule)` のようにまとめて送った時は、`処理` の最初に `2件をまとめて` と出ます
- **シートをまとめて読み込み**: 裏での読み込みで、キャッシュに無い表を Sheets API の1回で読んだ時間と枚数。
  その時の各表は `経費 30 miss(まとめて読み込み・12行×14列)` のように、行数×列数だけを出します
- **ログインの内訳**: `IDトークン確認`・`メンバーの照合`(メールアドレスから)・`版の読み込み`・`セッションの発行`・`最終ログイン日時の記録`
  (`1時間以内に記録済み` または `書き込み待ちに追加`)
- **応答の大きさ**: 往復の後の `応答 245KB`(本文の UTF-8 のバイト数)
- **裏での読み込みの内訳**: `裏での読み込み 1725(経費 400 miss(シート 350ms・12行×14列)・フォームの回答 600 hit・候補者 20・メール 300 miss・画像 40)`。
  `hit` はキャッシュから、`miss` はシートから読んだもの(その時は、シートの読み込みの時間と行数×列数も出ます)。候補者は、採用の権限が無い人にはシートを読まずに空を返します
- **getFiles の内訳**: `フォルダの設定`・`Drive`(ファイルを開く・フォルダの確認)・`画像のキャッシュ`(hit の件数)・`領収書の権限`・`ファイルの読み込み`
- **その他**(`otherMs`): 合計から、重ならない内訳を引いた残り。区間の中の内訳(認証の中のキャッシュの読み込みなど)は重ねて数えません。
  大きい時は、内訳に無い処理で時間がかかっています

### GAS の URL

団体の GAS の URL は、団体の担当者がレジストリに登録します(「Ohsumi」→「レジストリに登録する…」。
`registry/README.md` の「4.」)。メンバーは招待リンク(`<サイトの URL>/?org=<団体ID>`)から開き、画面がレジストリ(`REGISTRY_URL`)で
その団体の GAS の URL を調べます。送り先は、ページを開いた時に団体ごとに決まります(`lib/ohsumi/org-directory.ts`。
`registry/README.md` の「1.7. 接続先の解決」)。ビルド時に決まる「既定の団体」(以前の `CSV_GAS`)はありません。

- 登録するのは、デプロイの「ウェブアプリの URL」(`https://script.google.com/macros/s/<ID>/exec`)そのものです
- **`/u/1/` などを含む URL は使えません。** 複数の Google アカウントにログインしたブラウザのアドレスバーから
  コピーすると、この形になります。Google が転送し、POST の本文が失われます
- **`/dev` の URL は使えません**(編集者だけが使えるテスト用です)
- 団体の GAS は、登録の前にこの形を確かめ、違えば登録しません。レジストリの URL(`REGISTRY_URL`)は、
  ビルドの最初に形を確かめ(`scripts/check-registry-url.mjs`)、違えばビルドを止めます(値そのものは表示しません)

**反映の順番:** どちらからでも構いません。以前の GAS は `requestId` を無視し、以前の画面は `retryLater` を
無視するだけです。ただし、二重の書き込みを防ぐのは GAS 側なので、**GAS を先に**反映することをおすすめします。
ログインの送り直しも同じです。画面だけ先に反映すると、以前の GAS は送り直しを「既に使われています」で拒否します
(これまでどおり、もう一度ログインすれば使えます)。

## 4.5. 画像アップロードの保存先フォルダ

プロフィール画像・団体ロゴ・経費の領収書・アンケート設問の画像は、Apps Script が
管理する Drive フォルダに保存されます。GitHub Secrets への登録は不要です。

- `setupOhsumi()` を実行すると、スクリプトプロパティ `UPLOAD_FOLDER_ID` が
  なければ、Apps Script を実行しているアカウントの Drive に `Ohsumi uploads`
  フォルダを作成し、そのIDを `UPLOAD_FOLDER_ID` に保存します（既にあれば何もしません）。
- アップロード処理はこのフォルダだけを使います。
- アップロードしたファイルは、段階③(「10. 公開CSVからの移行手順」)以降は非公開で保存され、
  アプリは `getFiles` で権限を確認してから取得します。プロフィール画像・団体ロゴ・アンケート
  画像はログイン済みの全員、領収書はその経費申請を閲覧できる人(申請者本人・承認ステップの
  担当者・全権管理者・「経費」セクションを許可された役職)だけが見られます。
- 移行前のファイルが別のフォルダにある場合は、スクリプトプロパティ
  `LEGACY_UPLOAD_FOLDER_IDS` にそのフォルダのIDを登録してください(カンマ区切りで複数可)。
  `getFiles` はそのフォルダ内のファイルも返します。
- 領収書は5MBまで、画像(JPEG・PNG・HEICなど)とPDFのみアップロードできます。
- 既存のフォルダを使いたい場合は、`setupOhsumi()` の実行前に、スクリプトプロパティ
  `UPLOAD_FOLDER_ID` にそのフォルダのIDを登録してください。

`setupOhsumi()` を実行していない場合、アップロードは「Drive folder is not configured」
というエラーになります。

## 4.6. 設定の全員共有（Settings シート、任意）

要求スキル・カテゴリ・権限レベルなどの選択肢は、Settings シートに保存され、全員の画面で共有されます。

### 手順

1. スプレッドシートに **新しいシート** を追加し、シート名を **`Settings`** にする(`setupOhsumi()` を実行すると自動で作成されます)
2. 1行目に **`key`、`value`** の2列のヘッダーを入れる（データ行は空のままでOK）

以下の項目がそのままスプレッドシートに書き込まれ、次回以降は誰の画面を開いてもそこから読み込まれます:

| 設定キー | 内容 | 形式 |
|---|---|---|
| `skill_options` | 要求スキルの選択肢 | カンマ区切り文字列 |
| `category_options` | カテゴリの選択肢 | カンマ区切り文字列 |
| `roles` | 役職の一覧（「4.6.1. 役職」を参照。移行の後・新しく導入した団体で使う） | JSON配列 |
| `departments` | タスクの部門の一覧（「4.6.2. 部門」を参照。未設定なら既定の7部門） | JSON配列 |
| `role_levels` | 権限レベルの一覧（下位〜上位。`roles` が無い間だけ使う） | カンマ区切り文字列 |
| `role_permissions` | 権限レベルごとの管理画面表示範囲（`roles` が無い間だけ使う） | JSON文字列 |
| `project_templates` | プロジェクト種類ごとのテンプレートタスク | JSON文字列 |
| `task_set_templates` | 業務テンプレート | JSON文字列 |
| `recurring_rules` | 定期タスクのルール | JSON文字列 |
| `job_requirements` | ポジション要件（スキルマップ。`roles` が無い間だけ使う） | JSON文字列 |
| `skill_field_options` | 要求分野の選択肢 | カンマ区切り文字列 |
| `skill_field_skills` | 分野ごとの対応スキル | JSON文字列 |
| `skill_field_threshold` | 分野認定の閾値（0〜1） | 数値文字列 |
| `skill_level_thresholds` | スキルレベルアップの累計ポイント閾値 | JSON文字列（例: `{"デフォルト":100,"デザイン":150}`。移行後は `デフォルト` の代わりに `_default`） |
| `quiz_definitions` | 検定（クイズ）の定義 | JSON文字列 |
| `radar_axes` | レーダーチャートの軸定義 | JSON文字列 |
| `expense_categories` | 経費申請カテゴリと承認フロー | JSON文字列 |
| `custom_form_defs` | 団体カスタムフォームの定義 | JSON文字列 |
| `org_notification_emails` | 管理者向け通知の共有配信先メールアドレス | カンマ区切りメールアドレス |
| `project_order` | プロジェクトの表示順 | カンマ区切り文字列 |
| `one_on_one_questions` | 1on1ワークシートの質問項目（Admin → Tags の UI から設定可） | JSON配列（文字列） |
| `initial_tasks_json` | 初ログイン時に付与されるタスク一覧（未設定時はハードコードの3件） | JSON配列（各要素に `name`・`description`） |
| `inactive_notify_days` | 未アクセス通知の閾値（日数、デフォルト25） | 数値文字列 |
| `department_tree_config` | 部署ツリー構成（Admin → Org Tree の「部署を編集」から設定可。未設定時はメンバーの `department_path` から動的導出） | JSON配列（各要素に `path`・任意で `label`） |

> **`skill_level_thresholds`（スキルレベルアップ閾値）**: スキルポイントが何点に達したらレベルが上がるかを設定します。  
> 例: `{"デフォルト":100,"デザイン":150}` → デザインスキルは150点でレベルアップ、他は100点。

> **`expense_categories`（経費申請カテゴリ）**: Admin → 経費申請の承認カテゴリと多段階承認フローを定義します。

> **`initial_tasks_json`（初ログイン時付与タスク）**: 新規メンバーが初ログインしたときに自動付与されるタスクを定義します。  
> 例: `[{"name":"Ohsumiの使い方を確認する","description":"INPUT画面でタスクを登録してみましょう。"},{"name":"プロフィールを設定する","description":"スキルとWillを登録しましょう。"}]`  
> 未設定の場合はシステム組み込みの3件が付与されます。

> **`custom_form_defs`（カスタムフォーム）**: Admin → フォームで作成した団体独自の申請フォームの定義です。  
> こちらも Admin → フォームの GUI から編集できます。

### 4.6.1. 役職

役職は **上下関係の順（一般 → … → 最上位）** に並んだ一覧で、それぞれに **種類** があります。権限の判定は
種類だけで行い、役職の名前は見ません（名前を変えても権限は変わりません）。

| 種類 | 内容 |
|---|---|
| 最上位（`top`） | 代表専用の操作ができる全権管理者。1つ以上必要（既定は「代表」） |
| 管理者（`admin`） | 制限なし＝全権管理者。「制限あり」にすると、指定した管理画面のセクションだけが見える |
| 一般（`base`） | 管理者ではない。ちょうど1つ（既定は「一般」） |

- **保存先**: Settings に `roles`（JSON）がある団体（内部コードへの移行の後・新しく導入した団体）は `roles` に、
  無い団体（移行前）は今までの `role_levels`・`restricted_roles`・`role_permissions`・`job_requirements` に書きます。
  移行前は役職名が ID を兼ねるため、**役職の名前の変更と、代表以外の最上位の役職は、移行の後にできるようになります**。
- **メンバーの役職**（Members の `role`）は役職の ID（移行前は役職名）です。役職は ID でも名前でも引けるので、
  移行の途中で両方が混ざっていても同じ役職として扱います。経費・フォームの承認ステップの役職も同じです。
- **表示名**: 一般・最上位の役職の名前が既定（「一般」「代表」）のままなら、画面の言語に合わせて翻訳します
  （英語では General・President）。名前を変えた場合は、その名前をそのまま表示します。
- **削除**: 一般と、最初の最上位の役職は削除できません。使っているメンバー（休止中を含む）がいる役職は、
  Admin → Tags で移す先の役職を選び、メンバーを移してから削除します。
- **締め出しの防止**: 最上位の役職を持つ有効な（休止中でない）メンバーが0人になる操作（役職の変更・メンバーの
  削除・休止・役職の種類の変更・役職の削除）は、GAS が拒否します。

### 4.6.2. 部門

タスクの部門は、Settings の `departments`（`[{ "id": "ops", "name": "運営" }, …]`）に並んだ一覧です。未設定なら
既定の7部門（`ops` 運営・`pr` 広報・`dev` 開発・`design` デザイン・`relations` 渉外・`event` イベント・`research` リサーチ）を
使います。**未分類は部門ではなく空**で表します。Admin → Tags の「部門」で編集します（`departments` を手で書き換えないでください）。

- **タスクの部門の値**: 内部コードへの移行の前は部門名、後は部門 ID です。部門は ID でも名前でも引けるので、
  移行の途中で両方が混ざっていても同じ部門として扱います。移行前は部門名で引くため、**部門の名前の変更は移行の後に**できるようになります。
- **表示名**: 既定の部門の名前が既定のまま（運営など）なら、画面の言語に合わせて翻訳します。名前を変えた部門・
  足した部門は、その名前をそのまま表示します。
- **削除とアーカイブ**: タスク・テンプレート・定期タスク・権限の例外のどこかで使われている部門を削除すると、
  **アーカイブ**（`"archived": true`）になります。新しいタスクでは選べなくなりますが、今のタスクではそのまま表示され、
  絞り込みにも使えます（「アーカイブを解除」で戻せます）。どこでも使われていなければ一覧から消します。
- **タスクを別の部門へ移す**: 部門ごとに「タスクを移す」で、その部門のタスクをまとめて別の部門（または未分類）に移せます。

### 4.6.3. 内部コードへの移行（migrateToInternalCodes）

今まで日本語で保存していた選択肢の値（ステータス・難易度・優先度・重要度・公開範囲・承認状態・部門・日程調整の回答）と、
役職・部門を、画面の言語によらない内部コード・ID に書き換えます。Apps Script エディタから手動で実行します。

**手順**

1. GAS とフロントを、この機能の入った版に更新する（**GAS が先**）
2. スクリプトプロパティ `MIGRATION_MODE` が無い（または `dryRun`）ことを確かめ、エディタで `migrateToInternalCodes` を実行する（**dryRun**）
3. 実行ログを確かめる
   - シート・列ごとの変換される件数と例
   - **当てはまらない値**（変換せずに残す値。承認ステップの役職名のうち、役職の一覧に無いもの（削除済みの役職など）も含む）。
     必要なら手で直してから、もう一度 dryRun する
   - 移行後の役職の一覧（下の役職から順）と、それぞれの種類（管理者の役職は、全権か制限付きか）・人数
   - 役職を入れる位置。役職は「一般 → 管理者の役職 → 最上位の役職」の順に並べます
     - 役職の一覧に無かった役職名（メンバーの役職にだけあるもの）は、管理者の役職として作り、既存の管理者の役職の後ろ（最上位の役職のすぐ下）に入れます
     - `role_levels` で最上位の役職より後ろに書いてあった管理者の役職も、最上位の役職のすぐ下へ移します（管理者の役職どうしの順は変えません）
   - エラー（最上位の役職が見つからない、最上位の役職を持つ有効なメンバーがいない、など）
4. 最上位の役職の名前を「代表」から変えている団体は、スクリプトプロパティ `MIGRATION_TOP_ROLE_NAME` に最上位の役職の名前を入れて、もう一度 dryRun する
5. 問題が無ければ、`MIGRATION_MODE` を `apply` にして、もう一度実行する

**apply で行うこと**

1. ほかの処理と重ならないようにロックを取る
2. **スプレッドシートのバックアップのコピー**を自分のマイドライブに作り、**誰とも共有しない**状態にする（コピーの名前とURLは実行ログに出ます）
3. 列ごとにまとめて書き換える（Tasks・Members・経費申請（承認が済んだ過去の申請を含むすべての行）・Settings）
4. Settings に `roles`（ID 付きの役職）と `migrated_at`（移行した日時）を書き、スクリプトプロパティ `VALUE_FORMAT` を `codes` にする。
   今までの `role_levels` などは消さずに残します（`roles` があれば使われません）
5. データの版を上げ、`MIGRATION_MODE` を `dryRun` に戻す

何度実行しても結果は同じです（2回目は何も変わりません）。列は見出しの名前で探すので、列や設定が無い団体でも動きます。
移行の後、開いたままのタブは再読み込みするまで GAS に断られます（「ページを再読み込みしてください」と表示されます）。

**バックアップのコピーについて**

- コピーには **Apps Script（GAS）も一緒に複製されますが、コピーの GAS はデプロイしないでください**（同じ団体のデータの窓口が2つになります）。
  実行ログにも同じ注意を出します。
- コピーは誰とも共有しません。ほかの人と共有しないでください（メンバーのデータがそのまま入っています）。
- **削除してよい目安**: 移行の後、**1か月ほど問題が無ければ**削除して構いません。問題が見つかった時は、コピーから値を確かめて直すために使います。

### 4.6.4. Orbit からの移行の点検(migrationReport・renameOrbitCalendarEvents・listChangesFromOrbit)

Orbit から移す時に使う関数です(手順は `docs/orbit-migration-plan.md`)。どれもエディタから実行し、結果は実行ログに出ます。

| 関数 | 中身 | 使うスクリプトプロパティ |
|---|---|---|
| `migrationReport` | 移行の前と後で比べる数(行数・役職ごと・ステータスや部門ごと・見つからない参照・開けないファイルなど)を出す。読み取りだけ。前回の結果を覚え、次に実行した時に違う数だけを出す | `MIGRATION_REPORT_LAST`(前回の結果。関数が書く) |
| `renameOrbitCalendarEvents` | 実行するアカウントのカレンダーの、今日から2年先までの `[Orbit] タスク名` の予定を `[Ohsumi] タスク名` にする | `CALENDAR_RENAME_MODE`(無い・`dryRun`: 件数と例だけ / `apply`: 変えて dryRun に戻す)・`CALENDAR_RENAME_DIRECTION`(`toOrbit` で逆向き) |
| `listChangesFromOrbit` | 元の Orbit のシートを移行と同じ変換にしてから今のシートと比べ、追加・変更・削除された行を日本語の値で出す。読み取りだけ。メールアドレスは出さない | `ORBIT_SPREADSHEET_ID`(元の Orbit のスプレッドシートの ID)・`MIGRATION_TOP_ROLE_NAME`(移行の時に使った場合) |

## 4.7. Discord Webhook 連携（任意）

タスクが確認待ちになったとき、および期限超過タスクの日次サマリーを Discord チャンネルに通知できます。

### 手順

1. Discord で通知したいチャンネルの **「設定」→「連携サービス」→「ウェブフック」→「新しいウェブフックを作成」** → URLをコピー
2. Ohsumi のアカウントメニュー →「団体設定」の「Discord Webhook 連携」欄にURLを貼り付けて保存する(保存と同時にテストメッセージを送って接続を確認します)

Slack(Incoming Webhook)も同じ画面から設定できます。

Webhook URLは Settings シート（ログイン済みの全員に返る）には保存されず、Apps Script の PropertiesService（スクリプト専用の非公開領域）に保存されます。URLは保存後に画面へ表示されず、Apps Script も返しません。

- 団体設定の画面には、Discord・Slack それぞれ「連携済み」か「未連携」かと、最後のテスト送信の結果・日時が表示されます(`getWebhookStatus`。全権管理者と、Webhook を設定できる人にだけ返します)
- 未連携の場合はURLの入力欄が、連携済みの場合は「テスト送信」と「連携を解除」のボタンが表示されます
- URLを変更したい場合は、「連携を解除」してから入れ直してください
- テスト送信の結果・日時はスクリプトプロパティ(`discord_webhook_last_test` / `slack_webhook_last_test`)に保存されます。URLを変更・解除すると消えます

## 4.9. ほかの端末で開く(招待リンク・QR コード・自分のメール)

ログイン後のメニューの「ほかの端末で開く」で、今の団体の招待リンク(`<サイトの URL>/?org=<団体ID>`)を渡せます。
パソコン → スマホ、スマホ → パソコンのどちらにも使えます。リンクには**団体ID だけ**を入れます(セッション・メールアドレスは入れません)。

- **QR コード:** 画面の中で作ります(`lib/ohsumi/qr.ts`。外部のサービスに URL を送りません)。SVG で描くので CSP は変えていません
- **共有:** 端末の共有の画面(Web Share API)で送ります。共有の画面が使えない端末では、コピーのボタンだけを出します
- **自分のメールに送る:** 団体の GAS の `sendInviteLinkToMe` が、ログインしている本人の登録済みのアドレスにだけ送ります
  - 宛先は画面から受け取りません(送られてきても使いません)
  - 1人1時間に3回まで(`INVITE_MAIL_LIMIT`。送った時刻は CacheService に覚えます)。同じ `requestId` の送り直しは1通にします
  - サイトの URL は、レジストリの `checkIn` が配る一覧(`SITE_ORIGINS`。registry/README.md の「1.9.3」)から選びます。
    **レジストリに一度も確かめられていない団体では送れません**(画面のボタンが押せなくなります)。QR コード・共有・コピーは使えます
  - データを書き換えないので、**機能停止中(読み取り専用)も使えます**(`READ_ONLY_ACTIONS`)。提供停止中は、ほかの操作と同じく使えません
  - テスト環境では、ほかのメールと同じく `TEST_NOTIFICATION_EMAIL` にだけ送ります(未設定なら送りません。「11.」)
- 画面には、スマホで開いた後に「ホーム画面に追加」をすると次からすぐ開けることを、短く出します
- **反映の順番:** レジストリ → 団体の GAS → 画面。団体の GAS が古い間は、画面のメールのボタンは押せません(確かめられないため)

## 5. 承認・通知フローの説明

### タスク登録時の承認フロー

INPUT画面からタスクが登録されると `approval_status` が「承認待ち」になり、Admin → 承認 で管理者が確認するまでワークスペースには表示されません。

タスク登録と同時に `notify_new_task` が `TRUE` のメンバーへ通知メールが届きます。
1人も設定していない場合は、最上位ロールのメンバー全員に自動送信されます。

### 多段階承認

経費申請・カスタムフォーム申請は、Admin で定義した複数の承認者を順番に経由する多段階承認に対応しています。各ステップが承認されると次のステップへ進み、全ステップが承認されると申請が完了します。

### タスク確認フロー

担当者は「確認待ち」にするだけで「完了」にはできません。「完了」への変更は、タスクに設定された確認者（`reviewer_ids`）または全権管理者のみが行えます。
確認待ちになると通知先にメールが届き、Admin → Dashboard の「確認待ちパネル」にも表示されます。

### 確認待ちの複数承認

タスクに「確認者」を複数設定でき、「n人承認が必要」「全員の承認が必要」のどちらかを選べます。

**確認待ちの承認記録**: 確認者が「承認する」ボタンを押すと`review_approvals_json`に記録され、必要承認数に達すると自動的に「完了」になります。確認者が1人でも設定されているタスクは、確認者以外(全権管理者含む)がステータスを直接「完了」に変更することはできません(専用の承認フロー経由のみ)。

### プロジェクト健康状態の通知

Admin → Dashboard の「プロジェクト健全性」テーブルでは、期限超過/確認待ち/ブロック中タスクの件数から健康状態(良好/要注意/要対応)が自動判定されます。全権管理者は各プロジェクトの健康状態を手動で上書きできます(`health_override`)。手動で変更すると、結果に関わらず必ず幹部・管理者へ通知が飛びます。手動上書きしていないプロジェクトは、自動判定が新たに「要対応」になったタイミングで通知が飛びます(同じ「要対応」状態が続く間は重複通知しません。一度「要対応」以外に回復すると、次に悪化した際にまた通知されます)。

- 自動判定の通知は、管理者(「一般」以外の役職)が Ohsumi を開いたときに、その人のブラウザで判定して送ります(定期処理はありません)
- 宛先は他の管理者向け通知と同じです(`notify_new_task` が TRUE のメンバー。いなければ「一般」以外の役職のメンバー全員。加えて Settings の `org_notification_emails`)。Discord・Slack が設定されていればそちらにも送ります
- 健康状態が一度も記録されていないプロジェクト(新しく作ったプロジェクトや、この仕組みの導入前からあるプロジェクト)は、初回の判定では記録だけして通知しません
- 複数のプロジェクトが同時に「要対応」になった場合は、メール・Discord・Slack とも1通にまとめて送ります

### アンケート機能

ヘッダーメニューの「体験アンケート」から、メンバーは定点アンケートに回答できます。回答は各メンバー自身のMembersシートの行(`survey_responses_json`)に保存され、団体全体で共有されます(新規シートは使いません)。Admin → Analytics の「アンケート×人材データ組み合わせ分析」で、稼働量/ロール別/部門別/在籍期間別に平均スコアを集計できます。

## 8. メール通知が届かないときの確認手順

通知系の関数はメール送信に失敗してもタスクの操作自体は失敗させない設計のため、エラーが画面に出ません。原因切り分けは次の順で行ってください:

1. **`Code.gs` を編集したら必ず再デプロイする** — Apps Script エディタの保存だけでは既存のWebアプリには反映されません
2. **実行ログを確認する** — Apps Script エディタ左メニューの「実行数（Executions）」で問題の操作の直後の実行を確認する
3. **MemberEmailsシートを確認する** — 通知したい相手のメールアドレスが登録されているか確認する（`email`列はMembersシートではなくこちらの非公開シートにあります。`debugNotifyTest()` を実行すると実行ログにメンバーごとの登録状況が出ます）
4. **MailAppの1日あたり送信上限を確認する** — Apps Script エディタで `function checkQuota() { console.log(MailApp.getRemainingDailyQuota()) }` を実行して残り件数を確認する
5. **Webアプリの実行ユーザー設定を確認する** — 「実行するユーザー: 自分」になっているか確認する（「アクセスしているユーザー」になっていると失敗します）

## 8.5. 困ったとき(データを読み込めない・遅い)

1. **ブラウザを操作する AI の拡張機能を止めてください。** ページを読み取ったり操作したりする拡張機能
   (AI のアシスタント・エージェントなど)が入っていると、GAS への通信に割り込み、読み込みに失敗したり、
   GAS に GET で届いたりすることがあります。拡張機能を止めるか、拡張機能を使わないウィンドウ
   (シークレットウィンドウなど)で開き直してください。実行数の一覧に `doGet` が記録されている時は、実行ログの
   「doGet に届きました」の行(パラメータの名前と値の長さ)から、何から呼ばれたかの手がかりが得られます
2. **コンソールの `[ohsumi]` の行を見てください**(4.3 の表)。往復のうち GAS の中の時間が短く、echo の取得や
   打ち切りで時間がかかっている時は、GAS の処理ではなく、結果の受け渡しで止まっています
3. **コンソールで `ohsumiPing()` を実行してください。** GAS が何もせずに返す ping の往復時間と GAS の中の時間を並べて出します。
   ping でも往復が何秒もかかる時は、Google 側か回線側の問題です(Apps Script のコードや、スプレッドシートの大きさではありません)
4. **GAS の URL の形を確かめてください**(4.3 の「GAS の URL」)
5. 読み込みに失敗した時は、画面の「もう一度試す」を押してください
6. コンソールに Chrome の「The 'nonce' parameter should be passed within the 'params' object instead of as a top-level parameter」
   という警告が出ることがあります。これは Google のログインのライブラリ(Google Identity Services)が FedCM を呼ぶ時の書き方への警告で、
   Ohsumi のコードは FedCM を直接呼んでいません。ログインの動きには影響しません(Google がライブラリを更新すると消えます)

## 9.5. 数式インジェクション対策と既存データの点検

自由入力が書き込まれる列（タスク名・説明・カテゴリ・要求スキル・進捗メモ・
ブロッカーの理由、プロジェクト名・説明・目標、メンバー名・表示名・大学名等、
経費の領収書URL・理由・目的・差し戻し理由、候補者の氏名・電話番号・履歴書・
面接メモ、日報・週報の各本文、Settingsシートのvalue列）は、書き込み時に
セルの表示形式を書式なしテキスト（`@`）にしてから値を設定することで、
先頭が `=` `+` `-` `@` の値が数式として解釈されるのを防いでいます
（`Code.gs` の `FORMULA_INJECTION_PROTECTED_COLUMNS` /
`protectRowFromFormulaInjection_`）。Settingsのvalue列にはJSON文字列（
`role_levels`、`permission_overrides_json` 等）も入りますが、書式なし
テキスト化はJSON文字列の読み書きには影響しません。

この対策は導入後に新しく書き込まれる値にのみ効きます。

**性能上の理由から、Tasks/Projects/Members/Expenses/Candidates/
DailyReportsについては行を新規作成する時（`appendRow`の直前）にのみ
書式を設定し、その後の値更新（`updateRowFields_`）では毎回は設定し
直しません**（既存行のセルは作成時に既に書式なしテキストになっている
前提のため）。なお、Settingsシートは書き込み頻度が低いため例外的に
毎回設定し直しており、この制約はありません。

導入前から入っている既存データについては、**GASを新しいバージョンに
デプロイした直後に必ず** 次の2つの関数を、この順番で実行してください。
両者は性質が異なる別々の操作なので、意図的に関数を分けています。

1. `protectAllExistingRows()` — **値は一切変更せず**、既存の全行の
   保護対象列を書式なしテキスト（`@`）にします。中身を確認する必要が
   無い純粋な書式操作なので、確認なしで何度でも安全に実行できます。
   `updateRowFields_`が書き込みのたびに書式を設定し直さなくなったため、
   既存行の保護は基本的にこの関数の実行に依存します（後回しにすると、
   実行するまでの間に古い行が編集されても保護されません）。
   `setupOhsumi()`の実行時にも自動的に呼ばれるので、シートを作り直したり
   列を追加したりした後に`setupOhsumi()`を再実行すれば、この関数の
   実行を個別に忘れても既存行は保護されます。
2. `auditFormulaInjectionRisks()` / `auditFormulaInjectionRisks(true)` —
   **既にセルの値が数式として危険な状態になっていないか**を点検・修正
   します。`protectAllExistingRows()`とは異なり、`(true)`で実行すると
   値そのものが変わりうるため、まず引数なしで一覧表示して内容を確認して
   から`(true)`を実行してください。具体的な動作は以下のとおりです。
   - `auditFormulaInjectionRisks()` — 該当しそうなセルを実行ログに一覧
     表示するだけで、何も変更しません
   - `auditFormulaInjectionRisks(true)` — 一覧表示した上で、該当セルを
     修正します。修正内容はセルの状態によって次のいずれかです:
     - まだ数式として評価されていない（表示文字列が`=` `+` `-` `@`で
       始まっているだけの）セル: 書式を書式なしテキストにするのみで、
       表示内容（文字列そのもの）は変更しません
     - 既にSheets側で数式として評価されてしまっているセル: 書式なし
       テキストにした上で、元の数式の文字列（例: `=1+1`）をそのまま
       リテラルな文字列として書き戻します。これにより表示内容は
       計算結果（例: `2`）から元の入力文字列（例: `=1+1`）に変わります
       （数式としては実行されなくなりますが、表示上の値は変化します）

なお、この対策はGoogleスプレッドシート上で直接開いた場合や、Excel/ODS
形式でダウンロードした場合には有効ですが、CSV形式でダウンロードして
Excel等で開いた場合には効きません（CSVには書式情報が乗らないため）。

## 既知の制約

- **権限の判定に使うキャッシュ(スナップショット)と、スプレッドシートの直接の編集(運用上の注意)。** 初期データと、読み取り・普通の書き込みの認証(メンバー・役職・担当プロジェクト・権限の例外、担当者の確認に使うタスクの行)は、Members・Projects・Tasks・Settings のスナップショットを使います。
  - **権限そのものを変える操作**(代表だけ・全権管理者だけの操作と、メンバーの活動休止・部門・プロジェクトの担当の変更。`SHEET_AUTH_ACTIONS`)は、これまでどおりシートから読んで判定します。代表だけ・全権管理者だけの操作がこの一覧に入っていることは `lib/ohsumi/gas-write-auth.test.ts` で確かめています
  - **アプリからの書き込み**(メンバーの削除・役職の変更・部門の変更を含む、ロックを取るすべての書き込み)は、終わった時にデータの版を変えるので、**直後の読み取り・書き込みから新しい内容**で判定します(`lib/ohsumi/gas-ping-cache.test.ts`・`gas-write-auth.test.ts` で確かめています)
  - **書き込みは、ロックを取った後に版をもう一度確かめます。** スナップショットで判定した後に版が変わっていたら(ほかの書き込みで権限が変わったかもしれない)、シートから判定し直し、断られれば何も書きません
  - **スプレッドシートを画面で直接編集した時**は、編集・変更検知のトリガー(`onSpreadsheetEdit`・`onSpreadsheetChange`、`setupOhsumi()` が作る)が版を変えるので、通常はトリガーが動いた直後(数秒〜数十秒)から新しい内容になります。Members・Settings の編集は、スナップショットの版を変えます
  - **トリガーが無い・動かなかった時でも、スナップショットは作ってから最長5分で作り直します**(`SNAPSHOT_MAX_AGE_MS`)。つまり、直接の編集でメンバーを削除・役職を下げた場合、**最長5分間**は、そのメンバーが前の権限で読み取り(経費・フォームの回答・候補者・ファイルなど)と普通の書き込み(タスクの更新など)をできることがあります
  - **スクリプト・Sheets API・アドオンからメンバーや役職を書き換えた時は、トリガーが動きません。書き換えた後に、エディタで `bumpDataVersion()` を実行してください**(実行しないと、最長5分間は前の権限で判定されます)。メールアドレス表(MemberEmails)を書き換えた時は `resetMemberEmailsCache()` も実行してください
  - すぐに止めたい時は、直接編集ではなくアプリの管理画面から削除・変更するか、編集の後にエディタで `bumpDataVersion()` を実行してください(`revokeMemberSessions` でそのメンバーのログインも無効にできます)
  - `measureReadPerformance()` を実行するとキャッシュが無効になります
- ログイン用のメールアドレス表(MemberEmails)は、データとは別の版(スクリプトプロパティ `MEMBER_EMAILS_VERSION`)でキャッシュします。版が新しくなるのは、メールの登録・変更(メンバー追加・候補者のメンバー登録・メールの更新)、メンバーの削除、`setupOhsumi()`、スプレッドシートの手動編集(`onSpreadsheetChange`)のときだけです。メールを変えたのにログインできない場合は、エディタで `resetMemberEmailsCache()` を実行してください
- ログイン画面で「この端末にログイン情報を保存する」のチェックを外した場合、タブを閉じるとログアウトします。チェックありでも、Googleでのログインから30日たつと再ログインが必要です
- 定期タスクのサーバー側トリガーは `setupDailyTrigger` を一度手動実行しない限り動作しません
- 通知メールは Apps Script を実行しているGoogleアカウントの MailApp 経由で送られます（1日の送信数に上限あり）
- スキルレベル・カスタム項目・アンケート回答など、メンバー1行にJSON配列を持たせている列は、データが増えるとセルサイズに近づく可能性があります(Googleスプレッドシートのセル上限は約5万文字)
- 書き込みを伴う操作は`LockService`で排他制御しているため、複数人が同時に操作すると「混み合っています。少し待って再度お試しください。」と表示されることがあります。数秒待って再実行してください
- 利用者にそのまま見せてよいエラーメッセージは`throw new Error(...)`ではなく`throw userError_('...')`で投げること。目印(`isUserError`)の無い例外は`doPost`側で定型メッセージに変換され、詳細はLoggerにのみ記録される(`Code.gs`の`userError_`/`toErrorMessage_`参照)。新しいアクションを追加する際もこのルールに従うこと

## 10. 公開CSVからの移行手順

以前の版(シートを「ウェブに公開」してCSVで読み込む方式)から移行する場合は、次の順番で
反映してください。この順番なら、切り替え中も画面は壊れません。

1. **段階① GAS を先に反映する**
   `Code.gs` を貼り替え、「デプロイを管理」→ 既存のデプロイを編集 →「バージョン: 新バージョン」で
   公開します(Web App の URL は変わりません)。続けて `setupOhsumi()` を実行します
   (`onSpreadsheetChange` トリガーが登録されます)。この時点ではフロントは公開CSVのままで、
   画像も今までどおり表示されます。
   - 計測: Apps Script エディタで `measureReadPerformance()` を実行し、実行ログの
     「キャッシュなし」「キャッシュあり」の所要時間とデータ量を確認します
2. **段階② フロントを反映する**
   このリポジトリの変更を main にマージすると、GitHub Actions がデプロイします。再読み込みした
   人から新しい方式(ログイン後に Apps Script から読み込む)に切り替わります。古いタブを開いた
   ままの人は、公開CSVのまま動き続けます。
3. **段階③ アップロードファイルを非公開にする**
   Apps Script エディタで `makeUploadsPrivate()` を実行します。領収書から先に非公開になり、
   以後の新規アップロードも非公開で保存されます。途中で止まった場合は、もう一度実行してください。
   `auditUploadSharing()` で公開/非公開の件数を確認できます。
4. **段階④ 「ウェブに公開」を停止する**(段階②から1日ほど空けて、古いタブが残っていない状態で)
   スプレッドシートの **「ファイル」→「共有」→「ウェブに公開」** を開き、Members / Projects /
   Tasks / Settings それぞれの公開を停止します。あわせて GitHub Secrets の `MEMBERS_CSV`・
   `PROJECTS_CSV`・`TASKS_CSV`・`SETTINGS_CSV` を削除します。

## 11. 性能計測用のダミーデータ(テスト環境専用)

本番に近い規模で `measureReadPerformance()` を試すための関数です。**本番のスプレッドシートでは実行しないでください。**
スクリプトプロパティ `TEST_ENVIRONMENT` が `true` のときだけ動きます。

`TEST_ENVIRONMENT` が `true` のときは、アプリが送るメールも本来の宛先には届きません。

| スクリプトプロパティ | 動き |
|---|---|
| `TEST_NOTIFICATION_EMAIL` を設定した場合 | そのアドレス1つにだけ送ります(件名の先頭に `[テスト]`、本文の先頭に本来の宛先) |
| `TEST_NOTIFICATION_EMAIL` が未設定の場合 | 送信せず、実行ログに件名と本来の宛先を記録するだけにします |

カレンダーの予定も、テスト環境ではゲストを付けずに作ります(招待メールを送りません)。
Discord・Slack への通知は、テスト環境では**投稿せず、実行ログに記録するだけ**にします(管理画面の接続テストも行いません)。Webhook の動作を確かめたい時だけ、スクリプトプロパティ `TEST_ALLOW_CHAT` を `true` にしてください。
ダミーデータはメールアドレスを作りません(MemberEmails シートには行を追加しません)。

1. テスト用のスプレッドシート(本番のコピーなど)に `Code.gs` を入れ、スクリプトプロパティ `TEST_ENVIRONMENT` を `true` にする
2. `seedPerformanceTestData()` を実行する
   - メンバー50人(代表1・事業責任者2・班長7・一般40)、プロジェクト20件、タスク500件を追加します
   - タスクは幹部限定が約10%、承認待ちが約5%、コメント付きが約35%、履歴付きが約60%です
   - 追加した行の `id` はすべて `perf-` で始まります。ダミーデータが既にある場合は止まります
3. `measureReadPerformance()` を実行し、実行ログで所要時間とデータ量を確認する
4. `deletePerformanceTestData()` を実行してダミーデータを削除する(`id` が `perf-` で始まる行だけを削除します)
5. 読み込み方式ごとの計測(下の「12.」)も、同じダミーデータで行えます

## 11.5. 画面確認用のサンプルのデータ(テスト環境専用)

すべての機能が実際に使われている状態を再現し、画面が実際のデータでどう表示されるかを確かめるための関数です。
性能計測用のダミーデータ(上の「11.」)とは別のもので、両方を同時に入れても構いません。**本番のスプレッドシートでは実行しないでください。**

### 使い方

1. スクリプトプロパティ `TEST_ENVIRONMENT` を `true` にする
2. (任意)自分がサンプルのメンバーとしてログインして、立場ごとの見え方を確かめたい場合は、スクリプトプロパティ `TEST_ACCOUNTS` に
   テスト用の Google アカウントを**枠**ごとに書く(カンマ区切り)
   ```
   top=a@gmail.com, admin=b@gmail.com, restricted=c@gmail.com, base=d@gmail.com, base_en=e@gmail.com
   ```
   | 枠 | サンプルのメンバー | 立場 |
   |---|---|---|
   | `top` | 高橋 誠(`sample-m-01`) | 最上位(代表) |
   | `admin` | 伊藤 さくら(`sample-m-02`) | 全権管理者(事業責任者) |
   | `restricted` | 渡辺 大輔(`sample-m-03`) | 制限付きの管理者(サンプル班長。担当プロジェクトと、決めた管理画面だけ) |
   | `base` | 小林 陽太(`sample-m-05`) | 一般 |
   | `base_en` | Emily Carter(`sample-m-06`) | 一般・英語表示 |
   - 知らない枠の名前、**既にサンプル以外のメンバーに登録されているアドレス**(そのままではそのメンバーとしてログインしてしまうため)はエラーで止まります
   - メールアドレスを登録するのは、ここで割り当てたアカウントだけです(他のサンプルのメンバーには登録しません)
3. `seedSampleData()` を実行する
   - 既にサンプルがある場合は、消してから作り直します(何度実行しても重複しません)
   - 日付はすべて実行した日が基準です。期限切れ・今日締切・今週締切・来月開始・完了から日が経ってアーカイブされたタスクなどを、いつ実行しても再現します。
     日が経つと日付がずれるので、確認の前にもう一度実行してください
4. 確認が終わったら `deleteSampleData()` を実行する

### 入るデータ

- **メンバー20人**: 経歴・スキル・評価・研修・1on1 が豊富な人、ほぼ空の人(入ったばかり)、休止中の人、英語表示の人、とても長い名前の人など
- **プロジェクト8件**: 親子関係、アーカイブ済み、来月開始、期限切れで遅れているもの、健全度を手動で上書きしたもの、英語のもの、名前・説明がとても長いもの
- **タスク約150件**
  - 公募(応募者あり・なし)、承認待ち(一般・重要・対外公開)、幹部限定、確認待ち(複数の確認者・確認タスク)、修正中、依存関係、困っている・保留(理由つき)
  - 日程調整、フォーム、成果物・振り返り・工数・スキルポイント
  - 表示の崩れの確認用: とても長い名前・説明、コメント150件、担当者12人
  - 英語表示の人が担当する、英語の文章のタスク
  - 担当者の推薦(Will・Judgment・Fact)が意味のある結果を出すよう、スキルは担当者の Will・Judgment と合わせ、完了したタスクにはスキルポイントを付けています
  - 定期タスクから作られたように見えるタスク(週次定例の議事録)。サンプルの定期タスクのルールは**停止中**なので、新しいタスクは作られません
- **経費7件**(申請中・2段目の承認待ち・承認・却下・差し戻し・取り下げ・金額と説明がとても長いもの)、**フォームの回答3件**、**日報・週報**、**採用の候補者5人**
- **ダミー画像**: アバター・団体ロゴ・領収書(画像と PDF)・アンケートの画像を、アップロード用フォルダに**非公開で**作ります
- **Settings**: テンプレート・定期タスク・検定・学習・研修・アンケート・フォーム・経費のカテゴリ・人材DB の列・役職(サンプル班長)などを、**既存の設定を上書きせずに足します**
  - 団体名・ロゴ・テーマの色は、元の値をスクリプトプロパティ `SAMPLE_SETTINGS_STATE` に退避してから書き換えます
  - 選択肢の一覧(スキルなど)が空の団体では、画面の既定の選択肢に足します(既定の選択肢が消えないように)

### 削除(`deleteSampleData()`)

- `id` が `sample-` で始まる行を、すべてのシートから削除します
- テスト用のアカウントで操作して増えた行(サンプルのメンバーが作ったタスク・経費・フォームの回答・日報)も削除します
- Settings は、サンプルで足した分だけを取り除き、団体名・ロゴ・テーマの色は元の値に戻します。サンプルを入れた後に画面から足した設定は残ります
- ダミー画像はゴミ箱に移します。サンプルのメンバーの通知の待ち行列・ログインの世代番号も消します

### 通知について

- メールは、テスト環境では `TEST_NOTIFICATION_EMAIL` のアドレスにだけ届きます(上の「11.」)。サンプルのメンバーにはメールアドレスが無いので、届くのは割り当てたテスト用のアカウントの分と、団体メール(`org_notification_emails`)の分だけです
- 毎日の処理(期限切れの担当者への通知など)は、期限切れのタスクを担当しているテスト用のアカウント宛てに毎日送られます(`TEST_NOTIFICATION_EMAIL` に届きます)
- Discord・Slack は、テスト環境では投稿しません(`TEST_ALLOW_CHAT` が `true` の時だけ投稿)。サンプルを入れる時に Webhook が設定されていれば、実行ログに警告を出します
- プロジェクトの健全度は、初めて計算した時は通知しません。サンプルを入れても健全度の通知は送られません
- サンプルのメンバーの最終ログインは「実行した日の数日前」です。入れてから約25日たつと、未アクセスの通知の対象になります(もう一度 `seedSampleData()` を実行すると、日付が新しくなります)

## 12. 読み込み方式ごとの計測

現在の読み込み(`readSheetTables_`)は (d) の方式で、失敗した場合だけ (b) の方式で読みます。
(a)・(c) は採用していませんが、比較のために計測用の関数を残しています。

シートの読み込み方を4通りで計測し、シートごと・処理ごとの所要時間、セル数、データ量を実行ログに出します。
読み込むだけで、シートへの書き込み・データの版・キャッシュには触れません(本番で実行しても、利用者の
読み込みには影響しません)。失敗しても例外は投げず、実行ログにエラーを出して終わります。

| 関数 | 方式 |
|---|---|
| `measureReadA()` | (a) 以前の方式(シートごとにスプレッドシートを開き、`getDisplayValues`) |
| `measureReadB()` | (b) `getSheets()` を1回だけ呼び、`getDataRange().getDisplayValues()`(予備の読み方) |
| `measureReadC()` | (c) (b) と同じ取得で `getValues()` を使い、表示用の文字列に自前で変換 |
| `measureReadD()` | (d) Sheets API の `values.batchGet` を `UrlFetchApp` で1回だけ呼ぶ(スクリプトのトークンを使用。現在の方式) |

1. 1回の実行では1つの関数だけを実行します(同じ実行の中で続けて読むと、2回目以降が速く見えるため)
2. 各関数を3回以上(できれば時間を空けて)実行します。実行ログの「直近3回の中央値」を比べます
3. `showReadMeasurements()` で4方式の記録(各方式の直近5回)を一覧できます。`clearReadMeasurements()` で記録を消せます
   (記録はスクリプトプロパティ `READ_MEASURE_HISTORY_a`〜`d` に保存されます)
4. 「結果の一致」は、`getDisplayValues`(予備の読み方 (b))と同じ見え方で読めたかを示します。(c) は日付などの表示形式を見ないため、
   不一致のセルが出ることがあります(件数と例が出ます)

(d) で `HTTP 403 PERMISSION_DENIED / SERVICE_DISABLED` が出る場合は、「2.1.」の手順でサービスを追加してください。

### Sheets API の利用上限

Web アプリは「実行するユーザー: 自分」で動くため、全メンバーの読み込みが、デプロイした団体アカウント
1つからの Sheets API の呼び出しになります。Sheets API の読み取りの上限は、1分あたり
**プロジェクト全体で300回・ユーザーごとに60回**です(このため実質的には1分あたり60回)。

- Sheets API を呼ぶのは、スナップショットのキャッシュがない読み込み(アプリ経由の書き込み・手動編集の後の
  最初の読み込みなど)だけで、4シートを1回で読みます。キャッシュがあれば呼びません
- 上限に当たりうるのは、書き込みが頻繁に続く中で多くの人が同時に読み込む場合です(書き込みのたびに
  キャッシュが無効になり、次のキャッシュができるまでに読み込んだ人の数だけ呼び出しが発生します)。
  計測関数 `measureReadD()` の実行も1回に数えます
- 上限を超えると `HTTP 429` が返り、その読み込みは自動で (b) の方式に切り替わります(画面は動きますが、
  その分遅くなります)。実行ログの警告に `HTTP 429 RESOURCE_EXHAUSTED` と残ります
- このほか、`UrlFetchApp` の1日の呼び出し回数にも上限があります(個人の Google アカウントで2万回、
  Google Workspace で10万回。トークンの確認・Webhook 通知などと合算)
