# 設計書: コメント・変更の記録・1on1 の記録を、1件1行の別のシートに移す(まだ作っていない)

この文書は設計だけです。コードはまだ書いていません。公開の後に作ることを前提にしています。
関係する調査: [docs/gas-change-forecast.md](gas-change-forecast.md) の 1-7・2-5。

- 作業量は、テスト・README を含めた目安です(1日 = 1人の作業日)。
- 「団体の GAS」は gas/src(組み立てた gas/Code.gs)、「レジストリ」は registry/Code.gs、「画面」はこのサイト(lib/ohsumi・components/ohsumi)です。

## 0. まとめ

- **何をするか:** 増え続ける記録の一覧を、1件1行の新しいシート `TaskRecords`・`MemberRecords` に移します。
  - 今は1つのセルに JSON で入っています。
  - 対象は、タスクのコメント・進み具合の記録・変更の記録と、メンバーの 1on1 の記録・評価です。
- **画面と GAS の約束は変えません:** 操作の名前と送る形(差分 `listOps`)はそのまま、保存先だけを変えます。
  - このため、古い画面と新しい GAS、新しい画面と古い GAS のどちらの組み合わせでも壊れません。
- **移行のしかた:** 代表が移行の操作を実行します(自動では移しません)。
  - 実行の前に、自動でバックアップを取ります。
  - 途中で止まっても、続きから実行できます。
  - 最後に件数と中身を照合してから切り替えます。
  - 戻す関数もあります。
- **いつ要るか:** 5万文字の上限に届くのは、ふつうのタスク・メンバーではずっと先です。
  - 先に届きやすいのは「何でも書くタスク」のコメントと、毎週の 1on1 です。その場合は数か月〜1年で届きます。
  - それまでの間は、今ある「長くなっている記録」の警告(8割で知らせ、上限で保存を止める)で守れています。
- **作業量:** 9〜12日(GAS 5〜6・画面 2〜3・移行と戻す 2〜3)。
  - 兼部の統合表示([design-multi-org-view.md](design-multi-org-view.md))と同じ GAS の更新にまとめると、貼り替えは1回で済みます。

| Tasks | `progress_history_json` | 進み具合の報告 `{id, text, at, byId}` | 87文字 | 報告のたび。上限なし |
| Tasks | `history_json` | 変更の記録 `{id, field, from, to, byId, at}` | 107文字 | 変更のたび。**新しい50件だけ残す**(`LIST_ACTIONS.updateHistory.cap`。古いものは消える) |

### 1-2. 読み書きの今の流れ

- **読み取り:**
  - `getInitialData` が、Members・Projects・Tasks・Settings をまとめた「スナップショット」を返します(`25-read.gs`)。
  - スナップショットは版 `DATA_VERSION` ごとにキャッシュし、同じ版なら `unchanged` だけを返します。
  - 見せてよい行・列は、読み取りの権限表 `READ_POLICY` で絞ります。
    - コメント・変更の記録は、タスクの行が見える人全員に見せます(`all`)。
    - 1on1・評価は、本人と上長に見せます(`selfOrSupervisor`)。さらに項目ごとの公開範囲(`33-member-field-visibility.gs`)も効きます。
- **書き込み:**
  - 画面は一覧を丸ごと送らず、項目ごとの差分 `listOps`(add / update / remove。update と remove は変える前の内容 `before` 付き)を送ります。
  - GAS はロックを取ってから、今のセルの一覧に差分を当てて書きます(`applyListOps_`)。今の内容が `before` と違えば、競合として断ります。
  - 一覧の列は行の版(`row_version`)を変えません(`ROW_VERSION_IGNORED_FIELDS`)。
  - 一覧を丸ごと送る古い画面は、読み込み直してもらいます(`LEGACY_LIST_MESSAGE`)。
- **長さの守り:**
  - 1つのセルは5万文字まで(`CELL_MAX_CHARS`)です。超える保存は断り、書いた文章をコピーできる形で返します。
  - 8割を超えたら、書いた人と代表に知らせ、代表の画面の「長くなっている記録」に出します。
- **一覧の列を読み書きしている GAS のファイル:**
  - 共通: `03`(列の定義)・`11`(書き込みの入口・権限)・`13`(書き込み)・`21`(差分・長さ)・`26`(読み取りの権限)
  - コメント・進み具合・変更の記録: `18`(メンション・カレンダー)・`29`(バックアップから戻す)
  - コメントと 1on1 の数: `32`(週1回の集計値)
  - 変更の記録・1on1・評価: `33`(項目ごとの公開範囲)
  - 変更の記録: `12`(まとめた書き込み)

### 1-3. 上限(5万文字)に届くまでの見積もり

**測った値**(今のサンプル・見本のデータを GAS の `buildSampleData_`・`buildShowcaseData_` で作って数えた):

| データ | タスク / メンバー | いちばん長いセル | 上限に対して |
|---|---|---|---|
| サンプル(テスト環境) | 148 / 20 | コメント 15,503文字(1つのタスクに152件。崩れ確認のための多めの例) | 31% |
| 見本(デモの団体) | 44 / 11 | コメント 216文字 | 0.4% |

**1件の大きさの仮定**(サンプルは短い文なので、実際の利用に合わせて大きめにする):

| 記録 | 1件 | 上限に届く件数 |
|---|---|---|
| コメント | 150文字(本文 80文字 + ID・日時・メンション) | 約330件 |
| 進み具合の記録 | 150文字 | 約330件 |
| 変更の記録 | 110文字 × 最大50件 = 5,500文字 | **届かない**(50件で古いものを消すため) |
| 1on1 | 1,000文字(質問への答えを含む。300〜2,000) | 約50回(25〜160回) |
| 評価 | 800文字 | 約60回 |

**届くまでの時間:**

| 使い方 | 届くまで |
|---|---|
| ふつうのタスク(コメント 0〜30件、数週間で完了) | 届かない |
| 連絡用の「何でも書くタスク」(1日に4件) | **約80日** |
| 毎日進み具合を書く長いタスク(1日1件) | 約11か月 |
| 1on1 を毎週(1回 1,000文字) | **約1年**(長く書くと半年) |
| 1on1 を2週に1回 | 約2年 |
| 評価を年4回 | 10年以上 |

**FSIF の規模(仮定。違っていれば直してください):** メンバー40人、同時に進むタスク100件、1年で500件、1on1 は月1回とします。
- この規模でも、1件の記録が届くかどうかは、規模ではなく **1つのタスク・1人にどれだけ書くか** で決まります。
- 1年で届きそうなのは、上の「何でも書くタスク」と、1on1 を毎週長く書く人だけです。
- 本当の値は、代表の画面「長くなっている記録」(`getLongRecords`)のいちばん長いセル(`maxLength`)で確かめられます。公開から1か月後に一度見ることを勧めます。

**シート全体の大きさ:** 1つのスプレッドシートは1,000万セルまでです(`SPREADSHEET_CELL_LIMIT`)。
- 新しいシートは1件1行で約10列なので、10万件で100万セルです。FSIF の規模なら、数年は十分に入ります。
- 完了から日数がたったタスクの記録は、`TasksArchive` と同じく別のシートに移します(3-7)。

## 2. 方針

1. **画面と GAS の約束(操作の名前・送る形・返す形)を変えない。**
   - 書き込みは今の `listOps` のまま受けます。
   - 読み取りは、画面が「新しい形が読める」と伝えた時だけ新しい形で返します。伝えない画面には、今の形(行の中の `comments_json`)を組み立てて返します。
2. **移行は代表が実行する。** GAS を貼り替えただけでは、データを動かしません。
3. **移している間も、元のセルは消さない。** 照合して切り替えた後も、決めた日数(30日)は元のセルを残します。
4. **どの状態でも、どちらが正か(元のセル / 新しいシート)を、1つの印で決める。**
   - 印はスプレッドシートの中に置きます(バックアップから戻した時に、データと印がそろうように)。

## 3. 新しいシート

### 3-1. `TaskRecords`(タスクの記録)

| 列 | 中身 | 備考 |
|---|---|---|
| `key` | `<task_id>:<kind>:<entry_id>`(1行を決める鍵) | 同じ鍵の行は1つだけ |
| `task_id` | タスクの ID | |
| `kind` | `comment` / `progress` / `history` | |
| `entry_id` | 記録の ID(今の一覧の `id`) | |
| `at` | 書いた日時(ISO) | 並べ替えと、最近の分だけ読むのに使う |
| `by_id` | 書いた人のメンバー ID | 個人情報の削除・権限の確かめに使う |
| `reply_to_id` | 返信の元のコメントの ID(コメントだけ) | |
| `body_json` | 1件の中身(今の一覧の1項目を、そのまま JSON にしたもの) | 1件は2万文字まで(3-5) |
| `row_version` | 行の版(作る・変えるたびに新しくする) | 3-4 |
| `updated_at` / `updated_by` | 最後に変えた日時と人 | 読み取りでは返さない(`none`) |

- 中身は `body_json` にまとめて持ち、検索・権限に要る値だけを列に出します。
  - こうすると、記録に新しい項目が増えても、列を足さずに済みます。
- シートを作る時に、すべての列を書式なしテキスト(`@`)にします(数式として読まれないように)。
  - `body_json` は必ず `{` で始まります。

### 3-2. `MemberRecords`(メンバーの記録)

| 列 | 中身 |
|---|---|
| `key` | `<member_id>:<kind>:<entry_id>` |
| `member_id` | 記録の持ち主(今の Members の行の id) |
| `kind` | `one_on_one` / `evaluation`(後で増やせる) |
| `entry_id` | 記録の ID |
| `at` | 日付(1on1 は `date`、評価は評価の日) |
| `with_id` | 相手のメンバー ID(1on1 の `withId`。評価は評価した人) |
| `body_json` | 1件の中身 |
| `row_version` / `updated_at` / `updated_by` | 3-1 と同じ |

### 3-3. 読み取りの権限

- **`TaskRecords`:** 親のタスクが見える人(`canViewTaskRow_`)だけに返します。今の `comments_json: 'all'` と同じ意味です。
  - ゴミ箱・幹部限定・承認待ちのタスクの記録は、今と同じく見えません。
- **`MemberRecords`:** `kind` ごとに、今の列の規則をそのまま使います。
  - 1on1・評価は `selfOrSupervisor`(`READ_POLICY.Members.columns.one_on_ones_json` など)です。
  - 項目ごとの公開範囲(`33`)も同じく効かせます。
  - **規則が見つからない `kind` は、誰にも返しません**(今の「規則のない列は返さない」と同じ)。
- 権限の表は1か所(`26-read-policy.gs`)に置き、`kind` から今の列の名前に読み替えます(`RECORD_KIND_COLUMN = { one_on_one: 'one_on_ones_json', ... }`)。

### 3-4. 行の版と競合の確かめ

- 今の差分(`listOps`)の確かめ方を、そのまま行に当てます。
  - **add:** 同じ `key` の行があれば、中身が同じなら何もせず、違えば競合にします。
  - **update / remove:** その行の `body_json` を、送られた `before` と比べます(`canonicalJson_`)。違えば競合です。remove で行が既に無ければ、何もしません。
- 確かめと書き込みは、今と同じくスクリプトのロックの中で行います。
- `row_version` は、今の差分の確かめには使いません。将来、1件ずつの編集の画面を作る時と、バックアップから一部を戻す時の見分けに使います。
- タスク・メンバーの行の版は、今と同じく記録の変更では変わりません。

### 3-5. 1件の長さ

- 1件は1行の1つのセルなので、上限は5万文字のままです。1件ごとの上限を決め、値の確かめ(`37-value-checks.gs`)で断ります。
  - コメントの本文: 1万文字
  - 1on1 の `notes`: 2万文字
  - 評価: 2万文字
- 上限を超えた時は、今の `cellTooLong` と同じく、書いた文章をコピーできる形で返します。
- これで「長くなっている記録」の警告は、記録の一覧には要らなくなります。説明・設定の値などには残ります。

### 3-6. どの記録を移すか

| 記録 | 移すか | 理由 |
|---|---|---|
| コメント・進み具合の記録 | 移す | 上限なく増える。届くのがいちばん早い |
| 変更の記録 | 移す | 今は50件で古いものが消える。移すと上限を広げられる(1つのタスクに500件。古いものは毎日の処理で消す) |
| 1on1・評価 | 移す | 長い文になる。個人情報なので、読む時に絞りやすい形にしたい |
| 成果物・経歴・資格・研修・育成の計画・異動・スキル・アンケートの回答 | 今回は移さない | 増え方が遅い。必要になったら `kind` を足すだけで移せる形にしておく |

### 3-7. TasksArchive との関係

- 毎日の処理でタスクを `TasksArchive` に移す時、そのタスクの記録も **`TaskRecordsArchive`**(同じ列 + `archived_at`)に移します。
- 順番は今と同じく、先に移す先に足してから元の行を消します。途中で止まっても、次の回に `key` で重複を見分けて消すだけにします。
- 次の操作では、`TaskRecordsArchive` から読みます。
  - 移したタスクの検索(`searchArchivedTasks`)
  - 戻す(`unarchiveTasks`。記録も `TaskRecords` に戻す)
  - バックアップから一部を戻す
- ふだんの読み込みは `TaskRecords` だけを読みます。

## 4. 読み書きの流れ(移した後)

### 4-1. 読み取りと差分の読み込み

- 新しいシートは、スナップショット(4枚)に入れず、経費・フォームの回答と同じく **表ごとの版** で持ちます(`VERSIONED_TABLES` に `taskRecords`・`memberRecords` を足す)。
  - 関係の無い書き込みでは、キャッシュが捨てられません(コメントを書いてもスナップショットは読み直さない)。
- **初期データ(`getInitialData`):** 画面が新しい形を読めると伝えた時(4-3)だけ、`records` を足します。
  - 中身は、見えるタスクのコメント・進み具合のうち、**最近60日の分**(ベルの通知を作る期間 `COMMENT_NOTIFY_DAYS` と同じ)と、タスクごとの件数です。
  - `knownVersions` に表ごとの版を送ると、変わっていない表は `unchanged` で返します。
- **それより古い記録・変更の記録:** タスクを開いた時に、`getTaskRecords(taskId, kinds)` で読みます。
  - 結果は版ごとに、画面のメモリにキャッシュします。
- **1on1・評価:** 初期データに入れず、メンバーの画面の 1on1・評価を出す部分を開いた時に、`getMemberRecords(memberId, kinds)` で読みます(今は人材のページの経歴のタブ `career-tab.tsx` に出している)。
  - 個人情報を必要な時にだけ読みます。
- **GAS での読み方:**
  - シート全体を版ごとにキャッシュし(`loadVersionedRows_`)、権限で絞ってから返します。
  - 1つのタスクの記録を読む時も、キャッシュがあればシートを読みません。

### 4-2. 書き込み

- **操作の名前と送る形は変えません。**
  - タスク: `updateComments`・`updateProgress`・`updateHistory`
  - メンバー: `updateOneOnOnes`・`updateEvaluationHistory`
  - 送る形: `listOps`
- GAS は、移した後は `LIST_ACTIONS` の保存先を、セルではなく新しいシートにします(`cfg.store: 'rows'`)。
  - **add:** 末尾に行を足します。
  - **update:** その行の `body_json` などを書きます。
  - **remove:** その行を消します。
  - 親(タスク・メンバー)の行は、`createTextFinder` で `task_id` / `member_id` の列から探します。シート全体は読みません。
- メンション・返信の通知・カレンダー・週1回の集計値など、一覧を読んでいる処理は、「一覧を読む関数」を1つにまとめ、その中で読み先を分けます。
  - 読み先は、移す前ならセル、移した後なら新しいシートです。
  - 処理ごとに読み先を書き分けません。
- 変更の記録の上限(50件)は、移した後は500件にし、毎日の処理で古いものを消します。

### 4-3. 画面と GAS が互いを見分ける方法

- 画面は、すべてのリクエストに `clientFeatures: ['recordRows']` を付けます(今の `clientVersion` と同じ置き方)。
- GAS は、`getInitialData` の返事に `features: ['recordRows']` と、移行の状態(`recordRows: 'none' | 'migrating' | 'done'`)を付けます。

| 画面 \ GAS | 古い GAS | 新しい GAS(移す前) | 新しい GAS(移した後) |
|---|---|---|---|
| **古い画面** | 今のまま | 今のまま(GAS はセルを読み書きする) | GAS は行から `comments_json` などを組み立てて返し、`listOps` を行に当てる。**古い画面はそのまま動く** |
| **新しい画面** | `features` が無いので、今の形で読み書きする | 今の形で読み書きする(`recordRows: 'none'`) | 新しい形(`records`・`getTaskRecords`)で読む。書き込みは同じ `listOps` |

- 新しい GAS が古い画面のために一覧を組み立てる時は、親の行ごとに今と同じ形にします。
  - 並び順: コメントは古い順、変更の記録は新しい順
  - 5万文字を超える一覧は、新しい方から5万文字に入る分だけを返し、`truncatedLists` で知らせます。
  - 古い画面が丸ごと読むので、移した後に増えた分で超えることがあるためです。

## 5. 移行

### 5-1. 状態の印

- 印は `Settings` のキー `record_rows_state` に置きます。
  - `READ_POLICY` に規則を書かないので、画面には返しません。
  - 返す時は、`getInitialData` の `recordRows` として GAS が組み立てます。
- 値は JSON で、`{ "state": "none" | "migrating" | "done" | "failed", "since": ..., "by": ..., "version": 1 }` の形です。
- 印をスクリプトプロパティではなくシートに置く理由は、**バックアップから戻した時に、データと印がそろう** からです(5-6)。
- 途中まで進んだ位置(カーソル)は、スクリプトプロパティ `RECORD_ROWS_CURSOR` に置きます。
  - `{ source: 'Tasks.comments_json', afterRowId: '123', batch: 7 }` の形です。

### 5-2. 手順

代表が、ADMIN の「データの持ち方」(新しい項目)か、エディタの `migrateRecordsToRows({ dryRun })` で実行します。
今ある `migrateToInternalCodes`(B3)と同じ形にします。

1. **試す(dryRun):** 書き込みはしません。報告するのは次のとおりです。
   - 一覧ごとの件数
   - 読めない JSON の行
   - 同じ ID が重なっている記録
   - 1件の上限(3-5)を超える記録
   - かかる時間の見込み
   - 問題があれば、どの行かを出して、移行を止めます。
2. **実行の前の自動のバックアップ:** `createBackup_('beforeMigration')` でスプレッドシートを丸ごとコピーします。
   - 名前の末尾は「(移行の前)」にします。
   - 作れなければ、移行を始めません。
3. **書き込みを止める:** 記録の一覧への書き込みだけを止めます(印を `migrating` にする)。
   - 止めている間は、「データの持ち方を移しています。数分たってからもう一度お試しください」で断ります。
   - タスクの状態の変更など、ほかの書き込みは受け付けます。
   - 止めた印が30分以上残っている時(途中で止まった時)は、止めるのをやめ、元のセルを正として読み書きを再開します(`RESTORE_STALE_MS` と同じ考え方)。
4. **移す:** 一覧ごと・親の行の ID の順に、50行ずつ移します。
   - 1つの親の分を移すたびに、カーソルを保存します。
   - 足す前に、移す先の `key` の一覧を読み、**既にある `key` は足しません**(続きからやり直しても重ならない)。
   - 1回の実行は4分半までにします(Apps Script の1回の上限は6分)。終わらなければ、1分後に続きを実行するトリガー(`ScriptApp.newTrigger().timeBased().after()`)を作って終えます。
     - このための権限(`script.scriptapp`)は、すでにマニフェストにあります。
   - 止まった時は、次の実行(トリガー・代表がもう一度押す)が、カーソルの続きから始めます。
5. **照合する:** すべての親について、元のセルの一覧と新しいシートの行を比べます。比べるのは件数と、`canonicalJson_` にした中身のハッシュです。
   - 1つでも違えば、印を `failed` にし、どこが違うかを報告します。
     - 元のセルが正のままなので、利用者には何も変わりません。
     - 代表は「やり直す」(新しいシートを空にして 4 から)か、「やめる」を選べます。
   - 照合は移した後に、もう一度最初から全部を読み直して行います(移している間の書き込みと比べないように、3 で記録の書き込みを止めておく)。
6. **切り替える:** 印を `done` にし、表の版とスナップショットの版を上げます。
   - 結果を操作の記録(`AuditLog`)と代表へのメールに残します。
7. **元のセルを残す期間:** 切り替えた後も、元のセルは30日残します。この間、元のセルは書き換えません(古い値のまま)。
   - 30日たったら、毎日の処理で元のセルを空にします。
   - 空にする前の日に、もう一度だけ自動でバックアップを取ります。

### 5-3. 戻す関数

`revertRecordRows({ dryRun })`(代表。ADMIN とエディタ)を用意します。

1. 実行の前に、自動でバックアップを取ります(「(移行を戻す前)」)。
2. 新しいシートの行から、親ごとに今の形の一覧を組み立て直します(並び順は 4-3 と同じ)。
   - **移した後に書いた記録も含みます**(元のセルの古い値には戻しません)。
3. 組み立てた一覧が5万文字を超える親があれば、dryRun で一覧を出し、戻すのを止めます。
   - 代表はその記録を整理するか、戻すのをやめるかを選べます。
4. セルに書き、印を `none` にします。
   - 新しいシートは消さず、名前を `TaskRecords(戻した <日時>)` に変えて残します。
   - 30日後に、毎日の処理でゴミ箱に移します。
5. 戻している間は、5-2 の 3 と同じく、記録の一覧への書き込みを止めます。カーソルで続きからやり直せるのも同じです。

### 5-4. 移行の対象の団体と順番

1. まず、テスト環境(サンプルのデータ)で行います。
2. 次に、デモの団体(見本のデータ)で行います。
3. その次に FSIF で行います。
4. 最後に、ほかの団体の代表へ案内します。
   - 案内は、レジストリのお知らせと、管理画面の「データの持ち方」の知らせで出します。

- 移行は、急ぐ団体(「長くなっている記録」が出ている団体)から勧めます。
- 移さない団体も、新しい GAS のままで今と同じく動きます。

### 5-5. 個人情報の削除

- **退会したメンバーの個人情報を消す時(`purgeMember_`):** 今は 1on1・評価の列も空にしています。移した後は、`MemberRecords` の `member_id` がその人の行をすべて消します。
- **コメント・変更の記録の書いた人:** 今と同じく ID のまま残し、画面には「退会したメンバー」と出します。
- **ほかの人の 1on1 の記録の中で、相手(`with_id`)が退会した人の場合:** 今と同じく残します。
  - 1on1 の記録はその人のものとして扱っているためです。
  - 消す範囲を広げるかは、プライバシーポリシーの見直しと合わせて決めます(要確認)。
- **移した後30日、元のセルを残している間:** 消す処理は、元のセルも空にします(古いコピーに個人情報が残らないように)。

### 5-6. バックアップと戻す

- **毎日のバックアップ:** スプレッドシートを丸ごとコピーするので、新しいシートと印もそのまま入ります。変更は要りません。
- **全体を戻す(`restoreBackup_`):** 戻すシートに、新しいシートと `Settings` の印を含めます。
  - 戻したバックアップに新しいシートが無い場合(移行の前のバックアップ)は、今の新しいシートを空にし、印は `none` のまま(バックアップのとおり)にします。
  - 戻す前の画面(`previewRestore`)に、「このバックアップは、データの持ち方を移す前のものです。戻すと、移した後に書いたコメント・1on1 は、元に戻した中身に含まれません」と出します。
- **一部のタスクだけ戻す(`restoreTasks_`):** 今は一覧の列(`RESTORE_MERGED_TASK_LISTS`)を、バックアップと今の一覧で合わせています。
  - 移した後は、`TaskRecords` の行を `key` で合わせます。バックアップにあって今に無い行を足し、今の行は残します。
  - バックアップが移行の前のものなら、バックアップのセルの一覧から行を作って合わせます。

## 6. 版の決まり(古い画面・GAS と組み合わせても壊れない順番)

画面は全団体で1つのサイト、団体の GAS は団体ごとに貼り替えるため、**しばらくは古い GAS と新しい GAS が混ざります**。順番を次のとおりにします。

1. **レジストリ(最初):**
   - `KNOWN_GAS_VERSIONS` に新しい GAS の版を足します。
     - 最初は `required: false`(更新のお知らせだけ。まだ必須にしない)にします。
     - 新しい GAS で移行を一度でも行った団体が増え、問題が無いと分かってから `required: true` にします。
   - 移行を止めるスイッチ(`config.recordRowsMigration: 'allowed' | 'paused'`)を配ります。
     - 不具合が見つかった時は、全団体の移行を、レジストリから止められます。
     - スイッチが届かない時は、`paused` として扱います(安全な側)。
2. **団体の GAS(次):**
   - 4-3 の表のとおり、古い画面・新しい画面の両方を受けます。
   - 移行はしません(代表が実行するまで、今のセルのまま)。
3. **画面(最後):**
   - `features` を見て、新しい形と今の形を切り替えます。
   - 古い GAS の団体があるうちは、今の形を消しません。
   - 今の形を消してよいのは、次の2つがそろった時だけです。
     - レジストリの `minimum`(必須の版)が新しい GAS 以上になっている
     - レジストリの管理画面で、それより古い版の団体が0になっている
4. **してはいけないこと:**
   - 画面が新しい GAS を前提にすること(古い GAS の団体で、コメントが読めなくなる)
   - 新しい GAS が古い画面を断ること
     - ブラウザに残った古いタブがしばらく動くためです。
     - 断ってよいのは、`clientVersion` の仕組みで読み込み直しを促す時だけです。

## 8. テストの計画

- **GAS の単体(vitest のハーネス `gas-guard-harness`・`gas-org-harness`):**
  - 差分を行に当てる時の、add・update・remove と競合(今の `applyListOps_` のテストを、行の保存でも同じ結果になるように2回流す)
  - 読み取りの権限
    - コメントが見えるかは、タスクが見えるかに従う(ゴミ箱・幹部限定・承認待ち)
    - 1on1・評価は本人と上長だけ。項目ごとの公開範囲も効く
    - 規則の無い `kind` は返さない
  - 1件の長さの上限
  - 古い画面のための一覧の組み立て(並び順・5万文字で切ること)
- **移行:**
  - サンプルのデータで、dryRun の件数 = 移した件数 = 照合の件数になる
  - **途中で止める(批ごとに例外を投げる)→ 続きから実行 → 重なりが無く、照合が通る**
  - 同じ ID が重なっている・読めない JSON の行で、dryRun が止まる
  - 照合の失敗(わざと1行消す)で `failed` になり、元のセルが正のまま
  - 戻す: 移した後に足したコメントが、戻した後のセルにある
  - 戻す: 5万文字を超える親があると、止まる
- **組み合わせ(4-3 の表の6つのます):**
  - 古い画面の送る形(`listOps`)と読む形で、新しい GAS(移す前・後)を通す
  - 新しい画面で、古い GAS(`features` なし)を通す
- **バックアップ:**
  - 移した後に、移す前のバックアップへ全体を戻すと、印が `none` になり、セルから読める
  - 一部のタスクだけ戻すと、行が合わさる
- **個人情報の削除:** 退会した人の `MemberRecords` が消え、30日の間に残している元のセルも空になる。
- **移したタスク:** タスクと一緒に記録が移り、戻すと戻る。途中で止まっても重ならない。
- **通しテスト:**
  - `pnpm test:e2e` に「移行の前・移行・移した後」の流れを足す
  - テスト環境の団体での手での確かめ(移行の画面・移している間の書き込みの知らせ)
- **画面:**
  - `check:layout` に ADMIN の「データの持ち方」を足す
  - 1on1 を開いた時に読み込む間の表示

## 9. 危険と対策

| 危険 | 起きること | 対策 |
|---|---|---|
| 移行の途中で止まる(6分の上限・エラー) | 一部だけ移った状態 | 元のセルが正のまま。カーソルで続きから。`key` で重ならない。30分で書き込みの停止を解く |
| 照合をすり抜ける取りこぼし | 記録が消える | 件数とハッシュの両方で照合。元のセルを30日残す。実行前のバックアップ |
| 移した後に、古い画面が丸ごと読む一覧が大きくなる | 古い画面が重い・5万文字を超える | 古い画面には新しい方から5万文字分だけ返す。古い画面は読み込み直しで新しい画面になる |
| 新しいシートの読み書きが遅い | 保存が遅くなる | `createTextFinder` で親の行だけを探す。表ごとのキャッシュ。移行の前後で `measureReadPerformance` を測る |
| 古い GAS の団体で、新しい画面が新しい形を前提にする | コメントが読めない | `features` で切り替える。今の形を消す条件を、レジストリの数字で決める(6) |
| バックアップから戻した時の、印とデータのずれ | 読み先を間違える | 印をシートに置き、データと一緒に戻す。戻す前の画面で知らせる |
| 移行に不具合が見つかる | 多くの団体で記録が壊れる | 移行は代表が実行(自動ではない)。テスト → デモ → FSIF の順。レジストリのスイッチで全団体の移行を止められる |
| 個人情報が古いコピーに残る | 消したはずの 1on1 が残る | 元のセルを残す30日の間も、消す処理はセルを空にする。バックアップの保存期間(最長約3か月)は今と同じ |

## 10. 決めておきたいこと(要確認)

1. 退会した人が相手(`with_id`)の、ほかの人の 1on1 の記録を消すか(5-5)。
2. 変更の記録の上限を、50件から500件に広げてよいか(3-6)。
3. FSIF の規模の仮定(1-3)。
4. 移行を代表だけの操作にするか、全権管理者にも許すか。
