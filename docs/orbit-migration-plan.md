# Orbit から Ohsumi への移行計画

FSIF が今使っている Orbit(`FSIFofficial/Orbit`)のデータを、Ohsumi の1つの団体として移す計画です。
D1〜D5 は決めました(1.)。「新しく必要な部分」(4.2)の関数は、別の PR で作ります。

- **時期:** R1-d(接続先の解決)と、独自ドメイン(`ohsumi.fsif.jp`)への切り替えの後
- **`FSIFofficial/Orbit` のリポジトリは変えません。** Orbit の側で行うのは、スプレッドシート・Apps Script の画面での操作
  (デプロイの設定・トリガー・関数の実行)だけです
- 調べた版: Orbit は `main`(`gas/Code.gs` 約4,700行)、Ohsumi は `main`(R1-c の前)

---

## 1. 決めたこと

| # | 決めること | 決めた内容 |
|---|---|---|
| D1 | 移し方 | **Orbit のスプレッドシートのコピーに Ohsumi の GAS を入れる**(2.1)。元の Orbit は手を加えずに残るので、戻すのが簡単です |
| D2 | 切り替えの後の Orbit | **Orbit のサイトは止め(ログインもできない)、スプレッドシートを30日そのまま残す**(7.)。Orbit の画面で「見るだけ」を続けるには Orbit の GAS のコードを変える必要があり、今回の決まり(Orbit を変えない)と合わないためです |
| D3 | 戻す判断の期限 | **切り替えから3日以内**。それを過ぎたら、問題は Ohsumi の側で直します(7.1) |
| D4 | 書き込みを止める時間 | **約2時間を目安にし、予行演習でかかった時間を見て決める**(6.2) |
| D5 | ファイルを非公開にする時期 | **切り替えから30日後**(`makeUploadsPrivate`)。先に非公開にすると、戻した時に Orbit で画像・領収書が見えなくなります |

## 2. 移行の考え方

### 2.1. 移し方(コピーに入れる)

1. Orbit のスプレッドシートを「コピーを作成」します(Orbit と同じ Google アカウントが持ち主)
2. コピーの Apps Script を Ohsumi の `gas/Code.gs`・`appsscript.json` に入れ替え、新しいウェブアプリとしてデプロイします
3. コピーの中で `migrateToInternalCodes` を行い、レジストリに登録します

スプレッドシートをコピーしても、**スクリプトプロパティ・トリガー・「ウェブに公開」の設定・デプロイは付いてきません。**
このため、コピーの GAS は何も持たない状態から始まり、Orbit のデータを Ohsumi の GAS で読める形にそろえるだけで済みます。

**その場で入れ替える案をとらない理由:** Orbit のスプレッドシートの GAS を Ohsumi に入れ替えると、Orbit の画面は同じ GAS を使えなくなり、
戻す時にシートの値(コードに書き換えた値)まで戻す必要があります。

### 2.2. そのまま引き継ぐもの

- **ID:** メンバー・プロジェクト・タスク・経費などの ID は変わりません(コピーなので)。担当者・確認者・前提タスク・報告先などの参照もそのままです
- **ファイル:** プロフィール画像・団体ロゴ・領収書・アンケートの画像は、Orbit のアップロード先のフォルダにあるファイルを、
  URL(ファイル ID)のまま使います。ファイルは移しません
- **メールアドレス:** MemberEmails のシートごと引き継ぎます。ログインは今と同じ Google アカウントで行います

## 3. Orbit と Ohsumi の違い

### 3.1. シートと列

シートの名前は同じです。列は Ohsumi が Orbit の列をすべて持っていて、足りない列は `setupOhsumi()` が末尾に足します(既にある値は変えません)。

| シート | 違い | 移行ですること |
|---|---|---|
| Members | 同じ(Orbit の `setupOrbit` の一覧と Ohsumi の `MEMBERS_HEADERS` は同じ列) | なし |
| MemberEmails | 同じ(`id`・`email`) | なし |
| Projects | 同じ | なし |
| Tasks | Ohsumi の一覧に `hold_reason_note`・`hold_reason_since` がある。Orbit は保留の理由を書く時にこの2列を使うが、`setupOrbit` の一覧には無い(列が無い団体では書かれていない) | `setupOhsumi()` が無ければ足す |
| Settings | 同じ(`key`・`value`)。中のキーの違いは 3.3 | `migrateToInternalCodes` |
| Expenses・FormSubmissions・DailyReports・Candidates | 列は同じ | なし(値は 3.2) |

**読み方の違い:** Orbit は Members・Projects・Tasks・Settings を「ウェブに公開」した CSV で読みます。Ohsumi はすべて GAS から、ログインした人の権限で読みます。
**コピーのシートは公開しません**(コピーには公開の設定が付いてこないので、何もしなければ公開されません)。

**Orbit では画面に出なかったデータ:** Orbit の経費申請は、書き込みはシートに行いますが、読み取りはその端末の中だけでした。
Ohsumi では Expenses のシートから読むので、**Orbit で申請された過去の経費が、画面に出るようになります**。

1件の経費申請を見られるのは、次の人です(`gas/Code.gs` の `canViewExpense_`。今の申請も過去の申請も同じ決まりです)。

- 申請した本人
- その申請の承認の担当者
  - 承認ステップが「メンバー」なら、そのメンバー
  - 承認ステップが「役職」なら、**その役職を持つメンバー全員**(実際に承認した人だけではありません)
- 全権管理者: 最上位の役職(代表)と、制限の無い管理者の役職の人全員。**すべての申請を見られます**
- 管理画面の「経費申請」を許可された、制限付きの管理者の役職の人。**すべての申請を見られます**

Orbit では、`一般` 以外で `restricted_roles` に入っていない役職は、すべて全権管理者です(3.3)。
そのため、移行の後は、班長などの役職の人も過去の経費申請をすべて見られるようになることがあります。
**予行演習の dryRun の実行ログの「役職の一覧」で、全権管理者の役職と「経費申請」を許可された役職を確かめます。**
その役職名で、6.1 のお知らせの「〇〇」を埋めます。見せたくない役職があれば、切り替えの前に Orbit の設定を直すか、
移行の後に Ohsumi の管理画面(Tags の役職)で制限を付けます。
内容を事前に確かめます(8.)。

### 3.2. 選択肢の値

Orbit はシートに日本語で書きます。Ohsumi の移行前の形(日本語)と同じなので、`migrateToInternalCodes` がそのまま内部コードに書き換えます。

| 項目 | Orbit のシートの値 | Ohsumi の内部コード |
|---|---|---|
| ステータス | 未着手・保留・進行中・サポート必要・確認待ち・修正中・完了 | `todo`・`hold`・`progress`・`support`・`review`・`fix`・`done` |
| 難易度 | 誰でも可・新人歓迎・少し経験必要・経験者向け・上級者向け | `anyone`・`beginner`・`some_exp`・`experienced`・`advanced` |
| 優先度 | 高・中・低 | `high`・`medium`・`low` |
| 重要度 | 一般・重要・対外公開(空は一般) | `normal`・`important`・`external` |
| 公開範囲 | 全員・幹部(空は全員) | `all`・`leaders` |
| 承認状態 | 承認待ち・承認済み(空は承認済み) | `pending`・`approved` |
| 部門 | 運営・広報・開発・デザイン・渉外・イベント・リサーチ・未分類 | `ops`・`pr`・`dev`・`design`・`relations`・`event`・`research`・空 |
| 日程調整の回答 | ○・△・×(〇・✕ も) | `yes`・`maybe`・`no` |
| スキルの閾値の既定値 | `デフォルト` | `_default` |

**当てはまらない値**(手で入れた表記ゆれなど)は、dryRun の実行ログに「当てはまらない値」として出ます。変換せずに残るので、予行演習で一覧を作り、
本番の前に Orbit のシートで直すか、そのまま残すかを決めます。

### 3.3. 役職と権限

| | Orbit | Ohsumi(移行の後) |
|---|---|---|
| 役職の持ち方 | 役職名がそのまま ID。`一般` と `代表` だけが特別で、ほかの名前はすべて「班長と同じ管理者」 | Settings の `roles`(ID・名前・種類)。種類は最上位(`top`)・管理者(`admin`)・一般(`base`) |
| 役職の一覧・設定 | Settings の `role_levels`・`restricted_roles`・`role_permissions`・`job_requirements` | `roles` に移す(元のキーは消さずに残る) |
| 代表専用の操作 | `role === '代表'` | 最上位の種類の役職 |
| 制限付きの管理者 | `restricted_roles` に入っている役職 | 管理者(制限あり)。見える管理画面は `role_permissions` から引き継ぐ |
| 幹部限定タスク | `一般` 以外が見られる | 一般(`base`)以外が見られる(同じ) |
| 個別の権限の例外 | Members の `permission_overrides_json` | 同じ列・同じ形 |

`migrateToInternalCodes` の dryRun は、移行の後の役職の一覧・種類・人数・並び順を実行ログに出します。**Orbit で `role_levels` に無く、
メンバーの役職にだけある名前**は、管理者の役職として作られます(4.6.3)。予行演習で、この一覧が Orbit で意図している権限と同じかを代表が確かめます。

### 3.4. ログイン

| | Orbit | Ohsumi |
|---|---|---|
| 方式 | Google のアクセストークンを毎回 GAS に送り、GAS が Google に確かめる | Google の ID トークンで1回ログインし、以後は団体の GAS が発行したセッション |
| 必要なもの | GAS の `GOOGLE_OAUTH_CLIENT_ID` = Orbit のサイトのクライアント ID | GAS の `GOOGLE_OAUTH_CLIENT_ID` = Ohsumi のサイト(`ohsumi.fsif.jp`)のクライアント ID、`ORG_ID`・署名鍵(`setupOhsumi()` が作る) |
| 入口 | Orbit のサイト | Ohsumi のサイト。R1-d の後は団体 ID から接続先を調べる(招待リンク) |

メンバーは、切り替えの後に**新しい URL で一度ログインし直します**(Orbit のログインは引き継ぎません)。

### 3.5. ファイル(画像・領収書)

| | Orbit | Ohsumi |
|---|---|---|
| 保存先 | 画面の設定(GitHub Secrets の `DRIVE_FOLDER_ID`)のフォルダ | GAS のスクリプトプロパティ `UPLOAD_FOLDER_ID` のフォルダ |
| 共有 | **リンクを知っている全員が見られる**(`ANYONE_WITH_LINK`) | 非公開。`getFiles` で権限を確かめてから渡す(`makeUploadsPrivate` の後) |
| 以前のフォルダ | ― | `LEGACY_UPLOAD_FOLDER_IDS` に入れると、そのフォルダのファイルも使える |

コピーでは、`UPLOAD_FOLDER_ID` は `setupOhsumi()` が新しく作るフォルダにし、**Orbit のフォルダを `LEGACY_UPLOAD_FOLDER_IDS` に入れます。**
新しく上げるファイルは最初から非公開になり、Orbit のファイルは D5 の時期に `makeUploadsPrivate` で非公開にします。

### 3.6. スクリプトプロパティ・トリガー・通知

| もの | Orbit | 移行で |
|---|---|---|
| `GOOGLE_OAUTH_CLIENT_ID` | Orbit のサイトの値 | Ohsumi のサイトの値を入れる |
| Discord・Slack の Webhook(`discord_webhook_url`・`slack_webhook_url`) | スクリプトプロパティ | コピーには付いてこない。Ohsumi の管理画面から入れ直す(値はこの文書に書かない) |
| まとめて送る通知の待ち行列(`notif_queue_<メンバーID>`) | スクリプトプロパティ | 付いてこない。**書き込みを止める前に、Orbit で `sendBatchNotifications` を1回実行して送り切る** |
| 時間のトリガー(`sendBatchNotifications` 毎時・`dailyMaintenance` 毎日6時) | Orbit の GAS にある | **切り替えの時に Orbit の側を消す**(残すと、Orbit の側でも定期タスクの作成・期限切れの通知が動き、二重になる)。コピーには `setupOhsumi()` が作る |
| カレンダーの予定 | 件名 `[Orbit] タスク名` | Ohsumi は `[Ohsumi] タスク名` で探す。**Orbit が作った先の予定は、Ohsumi がタスクを変えても消えずに残り、二重になる**(4.2 の N2) |

## 4. 移し替えの手順の中身

### 4.1. 今あるもので行える部分

| 作業 | 使うもの |
|---|---|
| 足りない列・シートを足す、ログインの設定(`ORG_ID`・署名鍵)・トリガー・アップロード先のフォルダを作る | `setupOhsumi()` |
| 選択肢の値・役職・部門・スキルの閾値のキーを内部コードにする、`roles` を作る、`VALUE_FORMAT` を `codes` にする、移行の前のバックアップを作る | `migrateToInternalCodes`(dryRun → apply。gas/README.md の 4.6.3) |
| Orbit のフォルダのファイルを使う | スクリプトプロパティ `LEGACY_UPLOAD_FOLDER_IDS` |
| ファイルを非公開にする | `makeUploadsPrivate()`・`auditUploadSharing()`(gas/README.md の 10. の段階③) |
| レジストリに登録する | 「Ohsumi」メニューの「レジストリに登録する…」(registry/README.md の 4.5。代表がいるので、初期設定コードは作られない) |
| 予行演習でメール・カレンダーの招待・Discord に送らない | スクリプトプロパティ `TEST_ENVIRONMENT`(gas/README.md の 11.) |

### 4.2. 新しく必要な部分(実装は別の PR)

作った関数(`gas/Code.gs`。エディタから実行する。使い方は gas/README.md の「4.6.4.」):

| # | 関数 | 中身 |
|---|---|---|
| N1 | `migrationReport` | **移行の点検**(読み取りだけ)。行数・有効と休止中・役職ごと・ステータス・部門・優先度・公開範囲ごとの件数、見つからない参照(担当者・確認者・前提タスク・報告先など)、ファイルの URL の件数と開けないもの、Settings のキーを実行ログに出す。値は日本語でも内部コードでも同じ数になるようにそろえて数える。結果を覚え、次に実行した時に**前回と違う数だけ**を出す(Orbit のコピーに入れた直後 → apply の後、の順に実行すれば、違いだけが並ぶ) |
| N2 | `renameOrbitCalendarEvents` | **カレンダーの予定の名前**を `[Orbit] タスク名` から `[Ohsumi] タスク名` に変える(実行するアカウントのカレンダーの、今日から2年先まで)。既定は dryRun(件数と例だけ)。スクリプトプロパティ `CALENDAR_RENAME_MODE=apply` で変え、dryRun に戻す。`CALENDAR_RENAME_DIRECTION=toOrbit` で逆向き(戻す時) |
| N3 | `listChangesFromOrbit` | **戻す時の差分の一覧**(読み取りだけ)。スクリプトプロパティ `ORBIT_SPREADSHEET_ID` の元の Orbit のシートを、移行と同じ変換(役職の ID も同じ)にしてから今のシートと比べ、Ohsumi で**追加・変更・削除**された行を、Orbit に入れ直す形の日本語の値で出す。ログイン・通知で自動で変わる列と、移行の日時は出さない。メールアドレスは実行ログに出さない(変わったことだけ) |

## 5. 予行演習

**本番のデータのコピーを使うので、メール・カレンダーの招待・Discord・Slack を本当の宛先に送らないことが最優先です。**
コピーを作った直後は、コピーの中の Apps Script はまだ Orbit のコードです。**何も実行しないうちに**入れ替えます。

### 5.1. 用意

1. FSIF の Google アカウントで、Orbit のスプレッドシートを「ファイル」→「コピーを作成」します。名前は `【予行演習】Orbit → Ohsumi yyyy-MM-dd` にし、
   **「共有を同じユーザーにする」のチェックは外します**(コピーは自分だけのものにします)
2. コピーの「拡張機能」→「Apps Script」を開き、**何も実行せずに** `Code.gs` を Ohsumi の `gas/Code.gs` に、`appsscript.json` を Ohsumi の
   `gas/appsscript.json` に入れ替えて保存します(Sheets API のサービスが入ります)
3. 「プロジェクトの設定」→「スクリプト プロパティ」に入れます
   - `TEST_ENVIRONMENT` = `true`(**最初に入れる**)
   - `TEST_NOTIFICATION_EMAIL` = 予行演習をする人のアドレス(入れなければ、メールは送らずに実行ログに出すだけ)
   - `GOOGLE_OAUTH_CLIENT_ID` = Ohsumi のサイトのクライアント ID
   - `LEGACY_UPLOAD_FOLDER_IDS` = Orbit のアップロード先のフォルダの ID
4. エディタで `setupOhsumi` を実行し、権限を許可します。実行ログで、足した列(Tasks の `hold_reason_*` など)と、`VALUE_FORMAT` を変えていない
   (「既にデータがあるシート」)ことを確かめます
5. ウェブアプリとして**新しくデプロイ**し(次のユーザーとして実行: 自分、アクセスできるユーザー: 全員)、URL を控えます
6. `migrationReport`(N1)を実行し、**移行の前の数**として実行ログを保存します(同じ時刻の Orbit のシートの数と同じになるはずです)

### 5.2. dryRun → apply

1. `migrateToInternalCodes` を実行します(`MIGRATION_MODE` が無い = dryRun)
2. 実行ログを保存し、次を確かめます
   - 変換の件数(シート・列ごと)と例
   - **当てはまらない値**の一覧 → 本番の前に Orbit のシートで直すか、残すかを代表と決める
   - 移行の後の**役職の一覧・種類・人数・並び順** → Orbit で意図している権限と同じか、代表が確かめる
   - エラー(最上位の役職が見つからない・最上位の役職の有効なメンバーがいない など)
3. `MIGRATION_MODE` を `apply` にして、もう一度実行します。実行ログのバックアップのコピーの名前を控えます
4. `migrationReport`(N1)をもう一度実行し、実行ログの「前回と違う数」を確かめます(8.)
5. **かかった時間**を、`setupOhsumi` から apply の後の点検まで測ります(本番の書き込みを止める時間の見積もりに使います)

### 5.3. 動作の確認

R1-d の後の手順で、予行演習のコピーを**テスト用のレジストリ**に登録し、テスト用のサイトから入ります
(テスト用のレジストリが無い時は、`CSV_GAS` をこのコピーの URL にしたローカルの `pnpm dev` で行います)。

1. 役職の種類ごとに1人ずつ(代表・全権の管理者・制限付きの管理者・一般)、本人の Google アカウントでログインしてもらうか、
   テスト用のアカウントを MemberEmails に足して、その役職で入ります
2. 8. の「画面で確かめる」の項目を確かめます
3. タスクを1件作る・ステータスを変える・コメントする・経費を1件申請して承認する、を行い、シートに内部コードで書かれることを確かめます
   (メールは `TEST_NOTIFICATION_EMAIL` にだけ届く、カレンダーの予定にゲストが付かない、Discord に投稿されないことも確かめます)
4. `renameOrbitCalendarEvents`(N2)を dryRun で実行し、名前を変える予定の件数を確かめます(**予行演習では apply しません**。本番と同じカレンダーのため)
5. スクリプトプロパティ `ORBIT_SPREADSHEET_ID` に元の Orbit のスプレッドシートの ID を入れて `listChangesFromOrbit`(N3)を実行し、3. で行った変更が一覧に出ることを確かめます
6. **書き込みの止め方(6.2 の 3.)と戻し方(7.1 の 4.)を、予行演習のコピーのウェブアプリで試します**(Orbit の本番のデプロイでは試しません)。
   デプロイを編集して「アクセスできるユーザー」を「自分のみ」→「全員」と変えられること、戻した後も URL が変わらず、画面から使えることを確かめます。
   変えられない時は、6.2 と 7. の手順を見直します

### 5.4. 片付け

1. コピーのウェブアプリのデプロイをアーカイブし、トリガー(「トリガー」の画面)をすべて消します
2. テスト用のレジストリの登録を停止します
3. 予行演習のコピーと、apply が作ったバックアップのコピーは、本番の後まで残します(比べるため)。本番が終わって30日たったら消します

---

## 6. 本番の手順

### 6.1. 事前のお知らせ

| いつ | 何を |
|---|---|
| 2週間前 | 全員(メール・Discord): 切り替えの日時、書き込みが止まる時間、新しい URL(当日に案内する)、ログインし直しが要ること、Orbit はしばらく残ること、**過去の経費申請の見え方(下の文)** |
| 3日前 | 同じ内容をもう一度。書き込みが止まる時間の前に、書きかけの作業を保存するよう案内 |
| 当日・止める直前 | 「今から書き込みを止めます」 |
| 切り替えの後 | 新しい URL(招待リンク)と、ログインのしかた。問い合わせ先 |

**過去の経費申請のお知らせ(2週間前・3日前の文に入れる):**

> Orbit では、経費申請は申請した端末でしか見えませんでした。Ohsumi では、これまでの経費申請も画面に出るようになります。
> 過去の経費申請も、**申請した本人、その申請の承認の担当者(承認の役職の人を含む)、〇〇(全権管理者の役職と、「経費申請」を許可された役職)** が見られるようになります。
> 見られたくない申請があれば、切り替えの日までに〇〇(問い合わせ先)に知らせてください。

「〇〇」は、予行演習の dryRun の「役職の一覧」を見て、役職名で埋めます(3.1)。

### 6.2. 当日(書き込みを止める時間)

**止める前(Orbit):**

1. Orbit の Apps Script で `sendBatchNotifications` を1回実行し、まとめて送る通知を送り切ります
2. Orbit の「トリガー」の画面で、今あるトリガー(関数名・時刻)を控えます(戻す時に同じものを作り直すため)

**書き込みを止める(ここから時間を測る):**

3. Orbit のウェブアプリを「デプロイを管理」で編集し、「アクセスできるユーザー」を**自分のみ**にします。
   Orbit の画面は、ログインも書き込みもできなくなります(5.3 の 6. で試したやり方)
4. Orbit の「トリガー」の画面で、時間のトリガーを消します(`sendBatchNotifications`・`dailyMaintenance`)

**移す(5.1・5.2 と同じ。違うところだけ書きます):**

5. Orbit のスプレッドシートのコピーを作ります。名前は `FSIF Ohsumi`(本番)
6. コピーの GAS を入れ替え、スクリプトプロパティを入れます。**`TEST_ENVIRONMENT` は入れません**(本番)。`LEGACY_UPLOAD_FOLDER_IDS` と
   `GOOGLE_OAUTH_CLIENT_ID` は予行演習と同じです
7. `setupOhsumi` → デプロイ → `migrationReport`(移行の前の数)→ `migrateToInternalCodes` の dryRun。**予行演習の実行ログと比べ、違いが「その間に増えたデータ」だけか**を確かめます。
   思わない違い(新しい当てはまらない値・役職の変化)があれば、止めて判断します
8. apply → `migrationReport`(移行の後。前回と違う数が出る)→ 8. の数の確認
9. `renameOrbitCalendarEvents` を apply し(`CALENDAR_RENAME_MODE=apply`)、今日以降の `[Orbit]` の予定を `[Ohsumi]` にします
10. スクリプトプロパティに `REGISTRY_URL`・`OHSUMI_WEBAPP_URL` を入れ、「Ohsumi」→「レジストリに登録する…」で登録します
    (FSIF の管理画面で、団体名 `FSIF` の新しい団体の登録コードを発行しておきます)。**初期設定コードが出ないこと**を確かめます(代表がいるため)
11. 代表が新しい URL でログインし、8. の「画面で確かめる」を行います
12. 管理画面の「連携」で、Discord・Slack の Webhook を入れ直します

**開ける:**

13. 全員に新しい URL(招待リンク)を案内します。書き込みを止めた時間はここまでです
14. 当日中は、問い合わせとエラーの記録(GAS の実行ログ・監視の通知)を見ます

### 6.3. 切り替えの後

| いつ | 何を |
|---|---|
| 当日〜3日 | 毎日、`migrationReport` を実行して数が不自然に減っていないか確かめる。ログインできない人を個別に対応する(MemberEmails のアドレス違いが多い) |
| 3日後(D3) | 戻す判断の期限。これ以後は戻さず、Ohsumi の側で直す |
| 30日後(D2・D5) | 7.3 の「Orbit を閉じる」を行う |

## 7. 戻し方と、Orbit を残す期間

### 7.1. 戻す(切り替えから3日以内)

戻すのは、**Ohsumi では直せない問題**(多くの人がログインできない・データが欠けている・権限が大きく違う)が切り替えの後に見つかり、
3日以内に直す見込みが無い時です。

1. 全員に「Orbit に戻します。戻すまで書き込みをしないでください」と知らせます
2. Ohsumi(コピー)のウェブアプリの「アクセスできるユーザー」を**自分のみ**にします(書き込みを止める)
3. `listChangesFromOrbit`(N3)を実行し、切り替えの後に Ohsumi で作られた・変わった・消えたデータの一覧(実行ログ)を保存します
4. Orbit のウェブアプリの「アクセスできるユーザー」を**全員**に戻します(URL は変わりません。Orbit のサイトはそのまま使えます)
5. Orbit の Apps Script で、控えたトリガーを作り直します(`setupOrbit` が `sendBatchNotifications` を、`setupDailyTrigger` が `dailyMaintenance` を作ります)
6. 3. の一覧を見て、必要な変更を Orbit の画面から入れ直します(多ければ、代表と優先するものを決めます)
7. Orbit の URL を全員に案内します
8. Ohsumi(コピー)の時間のトリガーを消し、レジストリの登録を停止します。コピーは原因を調べるために残します
9. カレンダー: N2 で名前を変えた予定は `[Ohsumi]` のまま残ります。Orbit がタスクを変えた時に二重になるので、`renameOrbitCalendarEvents` を逆向き(`CALENDAR_RENAME_DIRECTION=toOrbit`・`CALENDAR_RENAME_MODE=apply`)に実行します

**3日を過ぎた後は戻しません。** Orbit と Ohsumi のデータの差が大きくなり、手で入れ直せなくなるためです。

### 7.2. Orbit を残す期間(30日)

切り替えから30日は、Orbit のスプレッドシート・GAS・フォルダを**そのまま**残します。

- Orbit のスプレッドシートは、FSIF のアカウントだけが開けます(メンバーには共有しません)。「当時の値を確かめたい」時は、代表が FSIF に頼みます
- **Orbit の画面で見るだけ、はできません。** Orbit の画面はログインに GAS を使うため、GAS を止めるとログインもできません。
  見るだけの形で残すには Orbit の GAS のコードを変える必要があり、今回は行いません(D2)
- ファイルは、Orbit のフォルダのまま・リンクを知っている全員が見られる形のままにします(戻した時に Orbit で表示するため)

### 7.3. Orbit を閉じる(30日後)

1. Orbit のスプレッドシートの「ウェブに公開」を、すべてのシートで止めます
2. Orbit のウェブアプリのデプロイをアーカイブします
3. Ohsumi(コピー)で `makeUploadsPrivate()` を実行し、`auditUploadSharing()` で「公開: 0」を確かめます(Orbit のフォルダのファイルが非公開になり、Ohsumi だけが権限を確かめて渡します)
4. Orbit のスプレッドシートを「アーカイブ」のフォルダに移します。消す時期は FSIF の保存の決まりに合わせます
5. 予行演習のコピーと、`migrateToInternalCodes` のバックアップのコピーを消します(5.4)

## 8. 移行の前後で確かめる項目

「前」は Orbit のシート(移行の前の N1)、「後」は Ohsumi(apply の後の N1)です。数は `migrationReport`(N1)で出します。

### 8.1. 数を比べる(N1)

| 項目 | 前と後で |
|---|---|
| Members の行数・有効(`inactive` でない)の人数・休止中の人数 | 同じ |
| MemberEmails の行数・メールアドレスが無いメンバー | 同じ(無い人はログインできないので、切り替えの前に直す) |
| 役職ごとの人数 | 同じ(Orbit の役職名と、Ohsumi の役職の名前が1対1) |
| 最上位の役職の有効なメンバー | 1人以上。Orbit の `代表` の人と同じ |
| `permission_overrides_json` がある人の数・例外の件数 | 同じ |
| Projects の行数・アーカイブ済み・親子の関係 | 同じ |
| Tasks の行数、ステータスごと・部門ごと・優先度ごと・公開範囲ごとの件数 | 同じ(値は 3.2 の表で対応する) |
| 担当者・確認者・前提タスク・関係する確認タスクの ID のうち、見つからないもの | 増えていない(0 が理想。前からあるものは一覧で確かめる) |
| Expenses・FormSubmissions・DailyReports・Candidates の行数、状態ごとの件数 | 同じ |
| Settings のキーの一覧 | 前のキーはすべて残る。`roles`・`migrated_at` が増える |
| 当てはまらない値 | 予行演習で決めたとおり(直した・残した) |
| `avatar_url`・団体ロゴ・領収書(`receipt_url`)・アンケートの画像の件数 | 同じ。どれも Ohsumi の `getFiles` で開ける(開けないものが0件) |

### 8.2. 画面で確かめる

| 項目 | 確かめ方 |
|---|---|
| ログイン | 役職の種類ごとに1人ずつ、新しい URL でログインできる |
| 権限 | 一般の人に幹部限定タスクが見えない。制限付きの管理者に、許可したセクションだけが見える。代表専用の操作(役職の変更など)が代表にだけできる |
| 班長のプロジェクトの範囲 | Orbit で班長が担当していたプロジェクトのタスクを、同じように操作できる |
| タスク | 一覧・カンバン・カレンダーに、前と同じ件数が出る。ステータス・難易度・優先度が前と同じ表示になる |
| 経費 | 過去の申請が、3.1 の決まりどおりの人にだけ出る(申請者・承認の担当者・全権管理者・「経費申請」を許可された役職)。一般の人には、ほかの人の申請が出ない |
| ファイル | プロフィール画像・団体ロゴ・領収書が表示できる |
| 通知 | タスクを確認待ちにすると、確認者にメールが届く(本番) |
| 定期タスク | 翌朝の `dailyMaintenance` で、定期タスクが Ohsumi の側でだけ作られる(Orbit の側で作られない) |
| カレンダー | 期限のあるタスクの日時を変えると、予定が1つだけになる(`[Orbit]` の予定が残らない) |
